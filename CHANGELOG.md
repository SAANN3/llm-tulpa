# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]
### Changed
- The system prompt now includes explicit guidance to verify images before attaching them and to treat initial conclusions as hypotheses rather than facts — using available tools to actually inspect, compile, or query state instead of inferring.
- `ui.attach_file` tool description clarifies that files should be attached directly to replies rather than suggesting external links or file hosts.
- Theme picker layout refined: nested list container, responsive grid with min-width constraints, scrollbar styling, and a scrollable settings panel body.

### Fixed
- A reply cut off by the token limit while the model was still reasoning (empty visible content, `done_reason: "length"`) was stored and shown as-is — an apparently blank turn, most often on models with long chains of thought (observed repeatedly with Qwen 3). This is now recognized as its own failure mode: the partial reasoning is kept as a message, and one automatic follow-up turn asks the model to answer based on what it had already worked out, with fresh budget. Separately, the per-request `num_predict` budget was being computed from an estimated character-to-token ratio that skewed conservative enough to often collapse to its floor on an ordinary prompt, cutting a reply short well before the real context ceiling; it's now anchored to Ollama's own reported token count from the previous turn (`chats.last_prompt_tokens`, reset after each compaction fold) instead of re-estimating from scratch every time, and the floor itself is raised to give a long reasoning trace enough room to actually finish. The nudge that asks the model to answer from its cut-off thoughts is a `notice` (the same muted, backend-written marker a finished-job notice uses) rather than a real chat message, so it doesn't render as something the user typed; compaction is checked against the full token count of that turn (prompt plus everything the model had already thought through), not just the prompt, so it can free room before the automatic follow-up if the conversation is already near the ceiling.
- Reopening a chat whose last tool call was cut short — the backend restarted while a command was running, or the page closed during it — re-ran that command automatically. A command that never exits (a dev server started in the foreground) then held the chat on "Thinking…" for the full ten-minute limit, every time it was opened. A call that the chat's permissions already allow and that was left unfinished is now recorded as interrupted, with a note to the model that it may have run only partly and was not repeated; a call waiting for the user's confirmation still waits. A second tool call for a chat that already has one running is refused, so a reload can't start the same command twice.

## [0.1.5] - 2026-09-20
### Added
- Accounts and multi-user isolation — the app now signs in. The first account created is the **owner**; only the owner can add or remove other users (from a new in-app Users page), and there is no open self-registration. Every chat, setting, uploaded file, and plugin configuration is scoped to the user who owns it — a second user sees none of the owner's data, and a cross-user access attempt 404s. Sessions are JWTs (`Authorization: Bearer`, 30-day TTL, `bcrypt`-hashed passwords), with a TUI login page and a shared axios layer that attaches the token and signs out on an expired one. New endpoints: `POST /api/auth/login`, `GET /api/auth/me`, owner-only `GET/POST/DELETE /api/users`.
- First-run setup wizard — a 10-step carousel that walks a fresh install through language, timezone, the PostgreSQL connection, the owner account (with a live password-strength meter), the LLM provider, the model to chat with, a theme, and notifications. The backend no longer needs a database configured to start: with none, it comes up in setup mode serving only `/api/setup/*` + login, and the wizard's database step (`POST /api/setup/database`) connects, migrates, and swaps the live services in without a restart. Connection details and an auto-generated JWT secret persist to a JSON config file (`data/settings.json` next to the binary, on every platform); The database connection is read only from that file — never from environment variables or `.env` — and `GET /api/setup/status` pings it, so a missing or unreachable database makes the frontend redirect every page to the wizard (as does any API call answering 503); Under Docker the same file lives in a host folder, `backend/data/`, so it can be edited by hand.
- Switchable models — providers and models are stored in the database (`llm_providers`, `llm_models`) and every chat is bound to one (`chats.model_id`, not null; new chats start with the user's default model and can be switched per chat or from Settings), instead of one model fixed by an environment variable at startup. A shared model picker (in the wizard's model step and the chat header's switcher) lists installed models with size/quant/estimated-memory requirements (`GET /api/llm/models`), and sets a chat's model (`POST /api/chats/model`; the model has to be installed). The owner can also browse Ollama's public library as JSON (`GET /api/llm/catalog`, parsed on the backend), pull a model or a Hugging Face GGUF (`hf.co/<user>/<repo>`) with live progress (`POST /api/llm/pull`), and import `.gguf` files already on disk — several at once, optionally paired with an `mmproj` for vision (each file's kind is read from its GGUF header, only projectors that fit the model are offered and a mismatched one is refused) — without downloading anything (`GET /api/llm/local_files`, `POST /api/llm/import`); pulls and imports run in the background and are watched at `GET /api/llm/tasks`.
- Graduated thinking-effort control — when the active model's own chat template supports a set of effort levels (e.g. `xhigh`/`medium`/`low`), the composer now offers them in a selector next to the existing thinking on/off toggle, and the chosen level is sent verbatim as `think` instead of a plain bool; the toggle itself still works exactly as before for any model. Which levels are offered is discovered live per composer mount from the model's own chat template (`GET /api/llm/thinking_capability` — a new endpoint that reads the template via Ollama's `/api/show` and extracts the exact strings the template's `reasoning_effort` check accepts, in the order it lists them), not hardcoded per model family and not cached anywhere: the active model can change without a restart, the call reads stored model metadata with no model load required, and a template with no recognizable thinking markers at all degrades to no control rather than one that would do nothing. Plain `true`/`false` behavior is preserved exactly for every call site that has no UI behind it (compaction, `llm.read_image`, messaging plugins, chat naming).
- Media previews for file attachments — image, video, and audio files attached by id (including files the model attached to its own reply via `ui.attach_file`) render in the preview popup, and an image's small attachment chip shows a real thumbnail instead of a generic file icon. The download route needs the session token, which a media element can't send, so the bytes are fetched with it and shown from a `blob:` URL.
- Every backend setting now lives in `data/settings.json` (Ollama's address and context length, the bind address, the files folder, the background-jobs folder and log retention, SearXNG, the model folder, the database) with `settings.example.json`/`settings.docker.example.json` listing them all — the backend reads no environment variables or `.env` any more. `MODEL_FILE` in `llm/` is optional.
- The `mtp` compose profile (`llm/compose.yaml`) — an optional raw llama.cpp server build with Multi-Token Prediction speculative decoding (`llama-mtp`) plus a small Ollama-to-OpenAI wire-format translator sidecar (`mtp-proxy`), since Ollama 0.34.0 has no `--spec-type`/MTP flag at all and silently ignores the MTP draft-head tensors some of our GGUFs already carry. Whether MTP helps turns out to be genuinely task-dependent — a clean, short-prompt benchmark and real, conversation-depth usage through the actual chat API don't necessarily agree — so it's meant for occasional per-task A/B rather than day-to-day use: it's kept fully configured and buildable but out of a plain `docker compose up -d` behind a named compose profile, so it doesn't load a model into the same card as `ollama` at once. `llama-mtp`'s startup flags mirror the Ollama service's KV-cache quantization, flash-attention, context length, and mmproj pairing so a comparison doesn't also compare different settings; `ollama.url` in the backend's `settings.json` pointed at `:11435` is all it takes to switch.
- Key facts — a durable companion to the compaction summary (`Chat.key_facts`: an optional goal plus a list of short facts). Where the narrative summary gets regenerated from itself on every fold and can gradually compress away specific detail, key facts are only ever appended to, never rewritten: each fold makes a separate, focused extraction call (existing facts shown only as "don't repeat this" context, never fed back in for the model to re-derive), and merging the result into what's already stored is a deterministic Rust function, not a model rewrite. Shown to the model as a distinct "Key facts (durable...)" block ahead of the narrative summary once a chat has any.
- `extensions/launcher` — a minimal, always-on-top desktop input bar (egui/eframe) for starting a chat without opening the browser first: type a prompt, press Enter, and it opens the frontend with that prompt already filled in and sent (a new `?prompt=` query param on the home page picks it up, creates the chat, and navigates straight there). Its random placeholder text comes from the same `POST /api/prompts/input_examples` the frontend itself uses, with a built-in fallback if that call fails. Three built-in themes (`slate`/`paper`/`matcha`, the same colors as those frontend themes) via `LAUNCHER_THEME`. See `extensions/launcher/README.md` for configuration and build instructions.
- The system prompt now asks for a brief (1-2 sentence) note before each tool call — what's about to happen, why, and what result is expected — and a brief check afterward on whether the result matched, including partway through a long chain of tool calls in the same turn. Aimed at a real, observed failure mode: a long agentic session producing tool call after tool call with empty visible content and enormous hidden thinking traces, which is both hard to follow from outside and a sign the model isn't checking its own progress along the way.
- Background jobs — `os.start_job`, `os.job_output`, `os.job_kill` and `os.list_jobs`. Starting a long-running command (a dev server, a watcher, a big build) with `&` inside `os.execute_command` leaves the model with no defined way to see how it goes: the output goes nowhere it can find, nothing tells it when the process ends, and nothing stops it from ending its turn saying it'll "wait". A job instead gets an id and a log file the tool owns (`jobs_dir` in `settings.json`, default `~/.llm-tulpa/jobs`, stdout and stderr interleaved), a row in a new `jobs` table tracking `running`/`exited` (with its exit code)/`killed`/`lost` (the backend restarted while it ran), and a watcher that records how it ended. `os.start_job` waits a bounded time (default 3s, at most 30) for an early exit, so "failed immediately" versus "still running" is part of what the call returns rather than something guessed from a delay — a missing program or a port already in use shows its error in the same result. Every job belongs to the chat that started it; another chat's job looks like it doesn't exist. Approving a command word covers both `os.execute_command` and `os.start_job` (one shared permission bucket, like the storage tools' folder grants), and the same blocklist applies to both. A finished job's log is kept for `job_log_retention_days` (default 7, `0` keeps them all) and deleted by a sweep when the backend starts — not when the job ends, since the model and the user still need to read it afterwards; `os.job_output` then reports that the log was cleaned up. Everything platform-specific about running a job (shell selection, detaching into its own process group, killing a whole process tree) lives in one module, `services/process.rs`, written for Unix and Windows — the Windows side is only cross-compile-checked, not run.
- Job notices and push. When a background job ends on its own, the model finds out without polling: at the start of that chat's next turn a `notice` message ("Background job 3 (`npm run build`) finished successfully (exit code 0)...") is persisted after the newest message already stored and before the model's reply — never between a tool call and its result — and reaches the model as a user-role message. The UI shows it as a muted marker in the timeline, in the same place after a reload; the turn's response carries it (`ChatOut.notices`) so what's on screen and what's in the database agree. A `GET /api/events` Server-Sent Events stream tells connected frontends a job finished (it's the backend's one channel for anything it needs to push — every event is a `type` in the same stream, so a new kind of event is a new variant, not new plumbing — and each page holds a single shared connection, opened only while a component is listening), and when the chat has no turn running the frontend starts one itself (`POST /api/agent/job_notices`, which decides server-side whether there's anything to report and does nothing if not, so a stale or duplicate hint is harmless); an event that arrives mid-turn is deferred until the turn ends, not dropped. A job whose outcome the model already saw in a tool result isn't reported a second time, and a job it stopped with `os.job_kill` never is. The system prompt tells the model it will be notified, so it can carry on or end its turn instead of waiting.
- `storage.read_file` takes an `offset` (characters to skip from the start) and reports `total_chars` and `next_offset`, so a file past the 40,000-character cap can be read in order, part by part, with the same tool — instead of the model running out of ways to see the rest and reaching for `os.execute_command` to `sed`/`tail` it. The truncation marker in the content names the range shown and the offset to continue from, and a read past the end of the file says so.
- Three new themes — Ember, Twilight and Cinder, warm dark palettes (amber on near-black, muted gold on deep blue-black, cream on charcoal) added to the picker on Settings and Setup alongside Slate, Paper and Matcha. Each is the same three color tokens every theme is, so nothing else needed to change; text contrast against the background is 8.8:1 or better on all three.

### Changed
- A shell command word approved for `os.execute_command` is now approved for `os.start_job` too (and the other way round), because both draw on one shared permission bucket. An approval granted before this change lived in `os.execute_command`'s own bucket and is not carried over — that command word gets asked about once more in each chat that had it approved.
- The database schema was rebuilt and normalized to 3NF for the per-user model: a `users`/`user_settings` split replaces the old global settings singleton, `chats` and `files` are owned by a user, message images/file-ids and the old plugin columns are normalized into join/side tables, and a single centralized migration is versioned by a `schema_meta` sentinel and never wipes data. **Upgrading from 0.1.4 keeps everything**: the old tables are moved into a `legacy` schema and, when the owner account is created in the setup wizard, the chats, messages, attachments, tool calls, permission grants, plugin settings and settings are copied over for it (the old tables stay as a backup).

### Fixed
- `os.execute_command` returned stdout and stderr uncapped, so a single oversized command output stored as a chat message could blow the model's context window on the next turn — Ollama then silently truncated the oversized history down to fit (no error anywhere in the pipeline, and that path shipped with zero logging), which excluded nearly the entire actual conversation, so the model's very next reply looked like it had genuinely forgotten everything. Stdout and stderr are now each capped independently at 40,000 characters — the same cap-and-truncation-marker convention as `storage.read_file` — and the tool's own description tells the model the cap exists and how to work around it for genuinely large output (narrower searches, byte-bounded pipes rather than line-capped ones), since that's exactly the kind of thing the model needs to know to not re-trigger the same failure.
- The `Select` dropdown panel (the thinking-mode selector's container, but any `Select`) always opened downward, so a trigger near the bottom of the viewport — the chat composer is exactly that, and it's where this control lives — clipped the panel off-screen and made every option past the first unreachable. It now measures the actual space below the trigger when it opens (not at mount — the trigger's position can change between opens) and opens upward when there isn't enough room below and more room above.
- Ollama's prompt cache was failing to match on almost every turn — llama.cpp's own logs showed as little as 3 tokens of a 47,000+ token prompt matching anything cached, forcing a full reprocess of the entire conversation history instead of just what's actually new, and turning prefill deep into a conversation into most of a turn's wall time (tens of seconds, sometimes over a minute, dwarfing actual generation). Two independent causes, both in what gets sent as the prompt's very first tokens (where the cache's prefix match starts, so any change there invalidates everything after it, no matter how much of the rest is identical to the last call): the system prompt embedded a fresh to-the-second timestamp on every single call, and each tool's parameter schema serialized from a freshly built `HashMap`, whose randomized per-instance iteration order changed the schema's literal text on every call even with identical tool definitions. Fixed by moving the timestamp onto whichever message is newest each turn (the new user turn, or a tool result — content that was never going to be cached anyway) instead of the static system prompt, and by switching the tool-schema map to a `BTreeMap` for deterministic ordering. Live-verified against a 275,000-character stress conversation: steady-state turns now reuse 90%+ of the cached prefix and complete in ~4-5s instead of ~40-70s at the same real context depth.
- Compaction's "how much recent history to keep verbatim" budget assumed roughly 2 characters per token — reasonable for English prose, but this project's actual traffic is agentic and tool/code-heavy, which measures closer to 2.3 real characters per token. That left barely any margin below the trigger threshold: the kept, not-yet-summarized tail could sit right at the budget's ceiling, leaving almost nothing eligible to fold on a given pass, so compaction re-triggered on nearly every turn — each time regenerating the summary/facts and re-paying a full prompt-cache miss — instead of settling comfortably below the trigger for a while. Lowered the assumed ratio to give real headroom for this kind of content.
- The per-request generation cap (`num_predict`) was a flat number matching the full context window, with no accounting for how many tokens the prompt itself had already used. On a turn with an already-large prompt, Ollama believed it still had the full cap's worth of room to generate — a real one hit this exactly while writing a large tool call: generation ran into the actual context ceiling mid-JSON, which llama.cpp can't gracefully stop, so the truncated tool call failed to parse and the whole turn errored out with nothing applied. `num_predict` is now computed per request from the prompt's own estimated size (character-based, calibrated to this project's real code-heavy ratio, with a `saturating_sub` rather than a subtraction that could silently wrap into a nonsense cap on an unsigned overflow) plus the actual serialized size of whatever tools are attached, so it always reflects genuinely remaining room rather than a number that ignores how full the context already is.
- `os.execute_command` waited for its stdout/stderr pipes to reach EOF, which only happens once every process holding the write end has exited — including anything the command backgrounded with `&`, which inherits them. Starting a dev server that way (`python3 -m http.server 8899 &`, an obvious thing for an agent to do) made the call never return, with no timeout anywhere, so the chat sat on "thinking" indefinitely with nothing logged and no error. Output now goes to scratch files and only the shell's own exit is waited on: a backgrounded process returns immediately and keeps running (its later output goes to an already-unlinked file rather than a closed pipe, so it isn't killed by a broken-pipe error the next time it logs). A foreground command that genuinely never exits is now killed, with its whole process group, after 10 minutes, returning whatever it had printed plus a note saying so. The tool's description points the model at `os.start_job` (see Added) for anything long-running, and says a `&` command's own output isn't captured anywhere it can get back to.
- An agentic turn could stop dead on a model reply that did nothing: the model wrote its tool call out as text — inside its reasoning, typically ending in a stray `</parameter></function></tool_call>` — instead of actually calling the tool, so no call was parsed, nothing ran, and the turn ended on an empty reply. Such a reply is now thrown away and generated again (up to twice) instead of being stored; only the reply that's kept is saved, and the time shown covers every attempt. Recognizing it needs no per-model knowledge: the wrapper tags to look for are read from the active model's own chat template (`<tool_call>`/`</tool_call>` for Qwen, whatever another model's template names), the same discover-it-live way as its thinking-mode levels, and a model whose template has none is left alone. A reply with no answer and no tool call that wasn't cut off by the token limit gets one regeneration, since that can also be a stall — but only one, because an empty reply is sometimes exactly what was asked for. A reply cut off by the token limit is never regenerated (it would hit the same wall), and a real tool call is never second-guessed.
- Debian bookworm's own packaged `rustc`/`cargo` (baked into the backend image for `os.execute_command`'s own use) is old enough to reject current-edition crates outright. Now copied from the build stage's own toolchain instead of installed via `apt-get` — that stage already has a current, verified-working Rust (it just built `backend` with it), so this costs no extra download and can't drift out of sync with whatever actually built the image.

## [0.1.4] - 2026-09-13
### Added
- File attachments: upload any file type to a chat (drag-and-drop, or the composer's picker), with previews for PDFs, Office documents, spreadsheets/CSV (rendered as a table), syntax-highlighted code, and plain text (also the fallback for any other extension whose content isn't binary). The model can read an attached file's actual content on request (`files.get_attached_file`), and can attach a file of its own to a reply (`ui.attach_file`) — landing on the actual message it prints, not an intermediate tool-calling one with nothing in it.
- `llm.read_image` — a tool that makes its own one-shot vision call on an image given by path, for an image the model found or was pointed to rather than one already visible to it inline in the conversation.
- Auto-confirm mode (Settings and Setup) — a local, per-browser toggle that resolves tool permission prompts automatically instead of showing them, for letting the agent run a task unsupervised.
- The backend's own container now permanently ships python3 (+pip, +venv), nodejs (+npm), go, rustc (+cargo), build-essential, git, jq, unzip/zip, curl, wget, poppler-utils, ripgrep, fd, tree, sqlite3, docx2txt, gnumeric, and Playwright + a real headless Chromium — plus a scoped, passwordless `sudo` covering just `apt-get`/`apt`/`dpkg`, so `os.execute_command` can install anything else on top freely (temporarily — only what's in this list survives a container restart).
- GUI passthrough — the host's display-server socket and `DISPLAY` are now passed into the backend container, so a GUI app launched non-headless (e.g. Playwright's Chromium) shows up as a real window on the host's own screen instead of only ever running headless.
- The system prompt now states its own deployment context up front — a private, self-hosted, single-user instance the user themselves builds and operates.
- `AGENTS.md` — onboarding for an AI coding agent working in this repo (how to run it, how to verify a change, doc/comment style, where each doc lives).

### Changed
- Ollama's KV cache can now be quantized (`OLLAMA_KV_CACHE_TYPE=q8_0` + `OLLAMA_FLASH_ATTENTION=1`) to trade some precision for a larger usable context window on VRAM-constrained hardware — opt-in via a deployment's own `llm/.env`, no default in the shared compose file. See `llm/README.md`.

### Fixed
- `OLLAMA_CONTEXT_LENGTH` could silently disagree between the backend and Ollama itself, since each read its own separate `.env` file — a single oversized tool result could then exceed what Ollama could actually accept, entirely silently (no log on the backend side, no error surfaced in the UI). Now sourced from one root `.env` for both; an Ollama request failure is logged with its actual status/body, and a failed turn now shows a visible, dismissible error in the chat instead of the "thinking" indicator just disappearing.
- `web.request` returned an HTML response as raw markup rather than its actual readable content — now converted via `html2text` before the size cap applies; its description also now points at the baked-in Playwright for anything JS-rendered, interactive, or screenshot-worthy.
- `storage.list_directory` had no cap at all, so a large enough directory's listing alone could exceed the model's context budget in one call — now returns at most 200 entries per call (sorted by name), with an `offset` argument to page through the rest.
- `web.search_query`'s `bing` engine was returning results with nothing to do with the actual query (almost certainly Bing's own scraper-hostility blocking SearXNG's engine) — replaced with `yandex`.
- `os.execute_command`'s destructive-command blocklist matched `dd`/`mkfs` as a raw substring anywhere in the command text, so unrelated text merely containing e.g. "sed dd od" as a list of tool names got permanently blocked with nothing to approve. Now only matches them as an actual leading word of a shell statement.
- A `LazyList` (the chat sidebar, message history) could end up scrolled to the wrong position after loading — its `jumpToTop`/`jumpToBottom` didn't update the list's own internal scroll anchor, so the very next unrelated render could drag the scroll position back to a stale computed value.
- A browser notification fired with an empty body when a reply's content came back blank (e.g. the model exhausted its output budget before producing an answer).

## [0.1.3] - 2026-09-05
### Added
- `os.*` extended with `get_date`, `get_process_list`, `get_network_info`, `cpu_usage`, `get_user_info`, `execute_command`, `env_read`, `env_write`. The agent's system prompt now also states the actual current date/time directly on every turn, so it doesn't assume a stale one from training.
- `storage.detect_file_type` — identifies a file by sniffing its first bytes rather than trusting its name.
- New `web.*` domain: `download_file` (save a URL straight to disk), `request` (GET/HEAD/POST/PUT/PATCH/DELETE, response read inline), and `search_query` (web search via a bundled local SearXNG instance) — see `backend/TOOLS.md`.
- New `searxng`/`searxng-nginx` Docker services backing `web.search_query`: a handful of solid search engines rather than SearXNG's full default roster, and calls are throttled at the container level so a burst of searches can't hammer the underlying engines.

### Changed
- Permission grants are now shared across every tool that needs the same kind of access, instead of each tool needing its own separate approval for the same thing — approving `storage.read_file` under a folder now also covers `storage.list_directory`/`storage.find_files`/`storage.detect_file_type` there, without a second prompt. Write and delete access remain separate, independent levels.
- `web.download_file` replaces the old `web.fetch_url` — downloads straight to disk instead of returning content inline, so it behaves the same whether the URL points at a text page, an image, or any other file type.

## [0.1.2] - 2026-08-30
### Added
- Vision — attach images to a message (frontend composer, or a photo sent through any messaging plugin) when running a vision-capable model. See the new "Vision" section in `llm/README.md` for pairing a model with a mmproj/CLIP projector.
- Messaging plugin: an optional `name_hint` setting tags every message handed to the agent with who actually sent it (name, user id, and send time, in a configurable timezone) — without it, several people talking to the same bot (e.g. a group chat) all look like one ongoing conversation.
- Telegram: multiple photos sent as one album now reach the agent as a single message with every image attached, matching how the frontend and Discord/VK already behaved.

### Changed
- The backend container now uses Docker's host network instead of its own bridge network, so it inherits whatever routing the host itself has (a VPN/proxy in particular) instead of losing it — see `compose.yaml`. Postgres and Ollama are addressed via `localhost` under this mode rather than their old Docker service names.
- The frontend's backend URL is no longer baked in at build time by default — an unset `VITE_BACKEND_URL` now falls back to whatever hostname the page itself was loaded from, so the same build works from `localhost`, a LAN IP, or anything else without a rebuild.
- Backend CORS now accepts any origin on port 5173, not just `http://localhost:5173`, to match the above.

### Fixed
- An image forwarded through a messaging plugin could make Ollama's vision decoder fail outright (`mtmd_helper_bitmap_init_from_buf: failed to decode buffer`), killing the whole reply — every image sent through a plugin is now decoded and re-encoded before it ever reaches Ollama, catching both unsupported formats and files Ollama's own decoder is unexpectedly picky about.

## [0.1.1] - 2026-08-27
### Added

- Redesigned UI — chat view, settings, tool confirmation/messages, theme preview, and message date separators.

## [0.1.0] - 2026-08-18
### Added
- Chat agent backend (Rust/axum) driving a tool-calling turn loop against Ollama, with full chat history persisted in Postgres and resumable across restarts.
- Real tool-calling: `storage.*` (read/write/edit/list/find files and directories) and `os.*` (hardware, disk space) — see `backend/TOOLS.md`.
- Per-tool permission system — anything that can actually change something asks first, with the option to allow once, allow for the rest of the chat, or refuse.
- Automatic history compaction so a long or tool-heavy conversation doesn't blow the model's context window.
- React frontend with a chat UI, settings/setup flow, and three themes (dark / white / matcha-dark).
- Docker packaging for the whole stack (`compose.yaml`), with real filesystem passthrough so the agent can read/write your actual files, and files it creates keep your own ownership.
