# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]
### Added
- Working notes. `chat.write_notes` saves the model's own notes for the chat (the plan, what is decided, file paths and function names it will need again; up to 8,000 characters, replacing the previous notes). They go out in the system message after the compaction summary on every request, and a fold never shortens them, because the summary keeps findings and leaves out plans. A write takes effect at the next compaction, not at once (the text stays in view in the model's own tool call until then), because changing the front of the prompt makes the model server read the whole conversation again. Right before a fold or a clearing pass the backend also asks the model, on the prompt the model server already holds (with the chat's own thinking setting, which a different setting would break the cache for), to rewrite its notes; an empty, `UNCHANGED`, over-long or tool-call reply leaves them as they were. The request is skipped when less than 16,000 tokens of the window are free, which is the case on a window of about 53k or less, and a fold that fails is not retried until the prompt has grown by 5% of the window. A system prompt rule asks the model to check the notes before a long task. Stored in `chats.notes` (schema 13).
- Old tool results are cleared to a one-line stub when the context passes the compaction trigger: the tool, its arguments, how many characters it returned and how it began, with a line saying to call it again for the content. The newest results stay in full up to 35% of the context window, the very last one always, and results under 600 characters are left alone. It runs before any model-written fold and, when it brings the estimate under 60% of the window, replaces it. The boundary is stored on the chat (`chats.cleared_up_to_message_id`), so the prompt is rebuilt byte for byte the same and the model server's cached prefix survives between turns.
- A setting, off by default, "Shorten old thinking in long chats" (`trim_old_thinking`). In the same pass as the tool results, thinking older than 10% of the context window is replayed as its last 1,500 characters, and the newest traces are replayed up to 24,000 characters instead of 10,000.
- After a fold the user's own earlier messages stay in the prompt word for word: the newest ones that fit in about 1,500 tokens (each cut at 1,500 characters), so a request is not left to a paraphrase in the summary. No place is kept for the first message, since in a chat that runs for weeks the original ask is the one most likely to be stale. A message that was cut, and the latest of the ones left out, name their ids for `chat.get_messages`.
- `storage.read_file` reads by line: `start_line` and `end_line` (from 1, inclusive). Its result carries `total_lines`, and a range cut by the 40,000-character limit names `next_start_line`; a first line that alone is over the limit comes back cut, with a `next_offset` to go on from. A new `max_chars` (at most 40,000, also the default) lets the model preview a file or a long line with a small number first. The description of `offset` now says it counts characters.
- `scripts/fake-llama/` is a scripted stand-in for `llama-server` and 26 scenarios that drive a backend against it (stop, permission, step limit, retries, folds, wake-ups, regenerate, events and more), each in a fraction of a second.
- `scripts/chat-metrics CHAT_ID` prints a chat's context use from the database (characters per kind, prompt peak, folds, prefill time, the `read_file` re-read rate), and `scripts/context-bench` runs a fixed agent task over the API for comparing context-management changes.
- A turn runs on the backend. `POST /api/agent/turn` stores the prompt and returns at once; the backend then asks the model, runs the tools it asks for and asks again until it answers, so closing the tab no longer stops a turn and two tabs can't run one twice (a second `POST /turn` on a chat with a run is refused with 409). `GET /api/agent/turn?chat_id=` says whether the chat is idle, running (since when, when the current model call started, tokens so far, the step and the step limit, the tool that is running) or waiting for permission, and how the last run ended (with when it started and its tokens). `GET /api/chats/messages` takes `after_id` for the messages newer than one the client has. `GET /api/live` carries `run_started`, `messages_changed`, `tool_started` and `run_ended` (answered, failed, stopped, step limit, waiting for permission).
- A tool call that needs the user's permission ends the run instead of waiting; `POST /api/agent/answer` takes one decision per pending call (`permanent`, `only_now` or `deny`) and the run continues. With auto-confirm on, the grants are made and the run goes on.
- `GET /api/agent/runs` lists the caller's chats that have a run going on, each with the state `GET /api/agent/turn` gives (a sub-agent's chat included, with the `parent_chat_id` of the chat that started it; a chat waiting for permission has no run and is not listed).
- The sidebar shows which chats are working: a small three-dot animation on the row while a run goes on (on the parent of a sub-agent that works), and, when the run has ended and the chat hasn't been opened, a check (answered or step limit), a lock (waiting for permission) or a warning (failed). It follows the backend's events on every page, so a run started in another tab or on another device shows up as it starts, and what ended while the page was closed is there when it opens. The browser notification for a finished run is sent from the same place, so it works on any page, and exactly one tab shows it however many are open (none while one is on screen).
- A "Debug output in this browser" switch in Settings (kept in the browser, applied at once, not part of the saved settings). While it is on, the app shows diagnostic details in the browser console and in a small panel in the corner of the page (for a phone, which has no console); today that is the server events a tab receives, each stream chunk and every reconnect, with the time and whether the tab is visible, which is how a tab that stops following the server is told apart from one the server never reached. The panel has a Copy button (the lines, with the page's address, the backend's address and the browser), and when the event stream can't be reached it also tries three short requests to tell a network that is down from a browser or content blocker that refuses that one address.
- A chat the user creates, renames or deletes appears, changes or goes in the chat list of their other open pages and devices at once (`chat_created`, `chat_renamed`, `chat_deleted` events).
- A chat remembers how its last run ended until its owner looks at it: `unseen_end` (`answered`, `waiting_for_permission`, `failed` or `step_limit`; a run the user stopped leaves none) is set when a run ends, cleared when the next one starts, and read from `GET /api/chats`; `POST /api/chats/seen` clears it and sends a `chat_seen` event, so the user's other open pages drop it too (`run_started` carries `parent_chat_id` for a sub-agent's run). A page opened later, on another device, knows which chats have news. Needs schema version 16, applied in place at start.
- `POST /api/agent/stop` stops a run: the model call in flight is dropped and nothing of it is stored.
- A per-user setting, `max_turn_steps` (none by default; `0` removes it): when a turn reaches it, the last model call is told the turn is about to be stopped and to write its conclusion, a tool call in that reply is refused with its text kept, and the run ends as `step_limit`. Needs schema version 14, applied in place at start.
- A finished background job or sub-agent starts a run on its chat by itself, with no browser open. A chat waiting for permission keeps the notice until the user answers.
- A tool result over a quarter of the context window is stored cut (its start, with a line saying how to ask for the rest), whatever the tool: a result bigger than the window can't be folded away and left the chat unable to send anything.
- The chat page follows the backend's run instead of driving it. Where the next reply will land it shows what the run is doing (thinking, or which tool is running and for how long), the run's total time and tokens (and "step N of M" when a step limit is set), with a Stop button; a reloaded page keeps counting from the real start, and every open tab on the chat follows the same run. A run that ends stopped, at the step limit or failed leaves a line at the end of the chat with how long it took and its tokens; the permission prompt answers go to `/api/agent/answer`. Settings gets "Use tools in new chats" and "Step limit per turn", and the chat header a "tools: on/off" switch.
- Tools can be switched off per chat, with a default in the settings (`use_tools`) that new chats take (an existing chat keeps its own value; `POST /api/chats/tools` changes it, and `tools_enabled` on `POST /api/chats` sets it at creation). A chat without tools sends the model no tool definitions (about 9,000 tokens), uses a short version of the built-in system prompt (the rules that don't mention a tool; a custom system prompt is sent as written), leaves out the tool references in the summary and pinned-message headers, and makes no notes request. For a small model, or a window the tool definitions would mostly fill. Needs schema version 15, applied in place at start.
- The summary header tells the model that what is not listed was dropped, and to read a value again with a tool (or, without tools, to say it no longer has it) instead of reconstructing it. In a 60-item task with one fold the model wrote 29 of 60 hashes in its final file from memory, wrong; the header is meant to stop that, but one run can't show how much it helps.
- A chat's key facts are bounded: at most 60 entries and 6,000 characters, each cut at 400 characters; the oldest go first except the first 10 (the task's own rules). A new fact that says nothing an existing one doesn't (same words, or a run of whole words inside it) is skipped, and one that contains an existing fact replaces it, so the list keeps the fuller wording. This is plain text comparison, not a request to the model. A 100-item task had left 81 facts, a small window 158, all riding in the system message on every request.
- A sub-agent's chat publishes `run_started` and `run_ended` like any run (a sub-agent that stops without handing anything back ends as `failed` with what it wrote), so a page that has it open follows it live.
- Rewinding (`POST /api/chats/rewind`) or deleting a chat that has a run going on is refused with 409: the run is building on those messages.
- Before a request is sent, its size is estimated from the last measured prompt plus what was added since (a large tool result), and the chat is compacted first when that passes the trigger.

### Changed
- The server-event stream moved from `GET /api/events` to `GET /api/live`. A path ending in `/api/events` is on common ad-blocker filter lists, and a page behind such a blocker was refused the stream by its own browser, so it never saw a run end, a chat created elsewhere or a finished job. The events themselves are unchanged.
- `POST /api/agent/regenerate` returns 202 and the new reply arrives like any run's. `POST /api/agent/chat`, `/continue`, `/use_tool`, `/can_use_tool`, `/allow_scope` and `/job_notices` are gone; the turn runner does what a browser did with them.

### Removed
- The `agent_history_len` setting (default 2000). It limited how many of a chat's newest messages were loaded for a turn and for a fold, so past that count the oldest messages after the compaction boundary dropped out of the prompt and out of the next fold without a word. What is sent to the model is bounded by compaction, by tokens; a chat that has grown past the window now fails visibly instead. A `settings.json` that still has the key keeps working (it is ignored).

### Fixed
- SearXNG and the rate-limiting proxy in front of it listened on every network interface (both run with host networking), so any device on the LAN could use the search instance, bypass its rate limit or use it up for the backend. Both listen on loopback only; the backend is their one client.
- The backend accepted an account with an empty or space-padded username, or an empty password, from the setup wizard's and the Users page's API (only the pages themselves checked), and quietly used only the first 72 bytes of a longer password. Such accounts are refused (400) with the reason.
- A messaging plugin's chat opened in the web UI (only by its address) could be sent a message there: it then ran with the full tool agent, beside the plugin's own agent, and the reply never reached the messaging app. Starting a turn or answering a permission prompt in such a chat is refused (409), as regenerating already was.
- `settings.json` was rewritten in place, so a crash or power cut while the backend saved it (the setup wizard, the model folder, server or Ollama settings) could leave it cut off; the backend then refuses to start, with the database connection and JWT secret in that file. It is now written to a temporary file and renamed over the old one, keeping its permissions.
- `os.env_write` changed the backend's own environment while it was running, which is undefined behaviour in a multi-threaded program and could crash it; the variable is now kept for the commands the backend runs (`os.execute_command`, `os.start_job`, which is what it was for) and `os.env_read` reads the same view. It also refuses `LD_PRELOAD` and the other variables that inject code into every later command.
- `storage.read_file`, `llm.read_image` and `ui.attach_file` read a file whole, so a model pointing one at a model file or disk image pulled gigabytes into the backend's memory; each now refuses a file over its limit (64 MB, 32 MB, 500 MB) before reading it. `storage.find_files` failed the whole search when one subfolder couldn't be opened (common in a home directory) and read every file whole for a content search; it now skips such folders and files over 16 MB.
- The web tools (`web.request`, `web.download_file`, `web.search_query`) followed a redirect to any host, so a host approved by name could send the call on to `localhost` or a LAN address without asking; a redirect is now followed only within the same host, and one to another host comes back as the answer with its address. They also had no timeouts (a server that never answered held the run forever, since Stop doesn't interrupt a running tool) and read whole responses into memory (a link to a large file could exhaust it): a request now has 120 seconds and reads at most 8 MB, a download is written to disk as it arrives, is given up after 60 seconds without data, and leaves no partial file when it fails.
- An approved shell command let any other command on the same line run without asking: approving `ls` covered `ls; rm -rf ~/x` or `cat x | sh`, since only a line's first word was checked. Every command a line runs (after `;`, `&&`, `|`, inside `$( )` and backticks, after `sudo` or `xargs` ...) now needs its own approval, and one prompt offers all of a line's missing commands at once; quoted text, comments and heredoc bodies don't count as commands.
- A `llama-server` left running by a backend that died without stopping it (a kill, an out-of-memory kill, a power cut: stopping it on exit only works for a clean exit) kept the port and the GPU memory. The next backend's own server failed at once, and the backend went on talking to the old one, so a model or context-window change silently did nothing. Before it starts a server the backend now stops any `llama-server` started for its port (wherever it came from), waits for it to be gone and for the graphics memory to be given back; a different program on the port is not touched, and the load fails with a message naming the port and `llama_cpp.port`.
- A page that could not reach the backend at all was treated as one without a database and sent the user to the setup wizard. It now shows a "Can't reach the backend" cover, asks again every few seconds and carries on by itself when the backend answers; the page under the cover is kept, so what was open is still there.
- A chat of many short tool calls could overflow the context window. The fold sized each message by its text and thinking only, leaving out the name and arguments of its tool calls (a `storage.write_file` call carries the whole file there) and what the chat template adds around a message, so with small results it found that "the recent history already fits" while the prompt was over the window, folded nothing, and the request was refused for being larger than the window.
- The reply-length cap counted the tool definitions twice once a prompt had been measured (the measurement already contains them), taking about 9,000 tokens from the room left for the reply. Near the compaction trigger of a 40k window that left only the 4,096-token floor, and a model that thinks first could be cut off mid-reasoning. The model's notes request, which needed 16,000 free tokens because of this, now needs 6,000.
- A compaction summary could be a tool call instead of a summary. The excerpt was a long transcript that ended on the agent's own last line, with the instruction far above it in the system message, and a model with thinking off continued that line; whatever was folded into it was lost. The instruction now comes after the excerpt, which is fenced as data, and a reply is stored only if it has the three sections and no tool call; otherwise it is asked once more, and if that fails the old summary stays and the fold is tried again later.

## [0.2.0] - 2026-10-04
### Added
- The setup wizard's database step comes filled in with the details of the PostgreSQL that starts with the app (`localhost`, `5432`, database `llm_tulpa`, user and password `postgres`), so a clean setup is a click on Next.
- The backend runs llama.cpp itself, as the default model provider. It starts `llama-server` as a child process on the first request that needs a model (or at boot with `llama_cpp.autostart`), switches between **launch profiles** (context size or automatic, KV cache types, flash attention, GPU layers, MTP drafting, vision projector and whether it runs on the GPU or the CPU — the CPU keeps its VRAM free at the cost of slower image reading —, extra arguments), unloads it after `llama_cpp.idle_unload_minutes` idle minutes and stops it when the backend stops. A model change is announced as a `model_state` event on `GET /api/events`. One server holds one model, so a request that needs a different profile waits its turn: the turn, greeting, chat name or summary in progress finishes first and is never cut off, requests are served in the order they came, and the chat page says it is waiting for the model. Only after 15 minutes of waiting is it refused with `423`, naming who has it, and the chat page then says so in a "Model in use" popup. A turn keeps the model it started on: switching a chat's model takes effect with the next prompt, not in the middle of the turn that is running. The Models page's **Model server** section (owner) sets how long an idle model stays loaded before it unloads and frees the GPU, whether the default model loads when the backend starts, and the load timeout — the idle time and the timeout apply at once and are kept in `settings.json` (`GET`/`POST /api/runtime/server`). Models are `.gguf` files in the model folder, which the owner chooses in the app (the wizard's model step or the Models page, with a folder browser; effective at once and kept in `settings.json`, `GET`/`POST /api/runtime/folder`, `GET /api/runtime/folder/browse`), and registered by the owner (`POST /api/runtime/models`, with the vision projector paired and MTP detected from the file) and removed by the owner (`DELETE /api/runtime/models?id=&delete_file=`: the entry only, or the `.gguf` file too, each asked twice in the UI; the launch profiles go with it, chats on it move to their owner's default model, its sampling presets stay as presets for any model that say "deleted model: <name>" (schema version 12), a turn running on it or being the only model there is refuses it, and an entry whose file is gone says "Missing file" and can be removed too); launch profiles are shared by everyone and written by the owner (`/api/profiles`); a new chat starts on the user's default model (the one chosen in the settings) with the launch profile chosen there too (`launch_profile_id` in `POST /api/settings`, kept in `user_settings.active_profile_id`, schema version 11; the model's first profile until one is chosen, and choosing another model clears it), and a chat then keeps what it runs on whatever it is switched to. Plain Ollama stays available as a second provider, and the two never hold the GPU together: before llama.cpp loads, Ollama is asked to unload whatever it has loaded, and a turn on an Ollama model first stops an idle llama-server (one with somebody mid-turn is left alone and Ollama makes do). `GET /api/llm/models` answers for one provider — `?provider=ollama|llama-cpp`, by default the provider of the caller's default model — with what Ollama has installed, or the registered llama.cpp model files with their size and quantization. See [`backend/README.md`](./backend/README.md) (`llama_cpp` settings) and `GET /api/runtime` (its `placement` says whether the loaded model is really on the GPU: from the launch profile's layer count and, on Linux with an amdgpu, i915 or xe driver, from the GPU memory the kernel reports the server holds — a model whose card is full and spills into system memory, or that runs on the CPU, is flagged on the Models page; llama-server's own log only says so at a debug verbosity that writes about eighteen lines per generated token), `/api/runtime/load|stop|logs|devices|test`.
- Ollama's address and context window are set in the app (the wizard's Ollama step and the Models page's Ollama tab, owner only), with a Test button that says whether an address answers and how many models it has. The address applies at once; the context window applies from the next start.
- Models page (`/models`, in the sidebar) with tabs **Models** (what is loaded and where it went — layers on the GPU, memory per device —, each model's launch profiles with Load, Test (tokens per second and the share of MTP drafts accepted), Edit, and for the owner New profile and the `.gguf` files that can still be added), **Download** (search Hugging Face for GGUF models, list a repository's files and download one into the model folder as a background task that resumes and checks the published sha256, after checking the disk has room for it — the free space is shown, a file that doesn't fit is greyed out and the backend refuses it with `409`; gated repositories are hidden until asked for and say a token is needed), **Presets** and **Hardware** (`llama-server --list-devices`). A fifth tab, **Ollama**, holds Ollama's own model management (pull from its library, import `.gguf` files) next to the rest. The chat header's model button (and Settings' default model) opens one chooser with a tab per provider — llama.cpp's models and profiles, Ollama's installed models — and a "Manage models…" button to this page. The home page's composer has the same chooser for the chat about to be started: a model (or launch profile) picked there is for that chat only, the default in the settings is untouched (`POST /api/chats` takes `launch_profile_id`, or `model` and `provider`), and the thinking levels offered follow it (`GET /api/llm/thinking_capability?model=&provider=` for a chat that doesn't exist yet).- Sampling presets: named sets of temperature, top-p, top-k, min-p, repeat and presence penalty and seed, per user, several per model (or for any model), one chosen at a time per model, with built-in templates to copy and export/import as a JSON file. The chosen preset is sent with every call to that model; nothing is sent for a value left empty, so the server's own default applies.
- Setup installs llama.cpp: a "llama.cpp" wizard step looks at the machine (CPU, memory, GPUs), suggests a build (CPU, Vulkan, ROCm, CUDA 12 or 13) with the libraries it needs that are missing and the command that installs them, and downloads it into `~/.llm-tulpa/llama` — the release this version was tested with (checked against its published sha256), the newest release (may break), or your own `llama-server` binary — then the model file to use. Linux x86-64 is the tested path; Windows, macOS and ARM builds are offered but untested. An install that was set up before this wizard step existed is offered the wizard again once, with a popup saying so, and the wizard can move its existing chats to the new model.
- A per-user Hugging Face token in the settings, for downloading gated models; it is never sent back to the browser.
- The model's chat template (which tells whether it can think, and how it marks tool calls) is read from the `.gguf` file itself, so opening a chat doesn't start the model. Each chat's context gauge and its history compaction use the context window of the chat's own launch profile.
- Docker: the backend image carries what the downloaded llama.cpp needs (OpenMP, Vulkan through Mesa); `./start-docker.sh` looks at the host's GPU and adds `backend/gpu-amd.yaml`, `backend/gpu-nvidia.yaml` (needs the NVIDIA Container Toolkit) or `backend/gpu-dri.yaml` to the stack, or you set `LLM_GPU=amd|nvidia|dri|none`. The model folder is mounted writable. The Ollama container is an opt-in profile (`--profile ollama`). `./start-native.sh` runs the backend on the host instead (for ROCm or CUDA speed) with the database, SearXNG and the frontend still in Docker, keeping its settings in `backend/data-native/`. The backend and the frontend each have a `compose.yaml` in their own folder, included by the root one like `postgres/`, `searxng/` and `llm/`. The image is Debian 13, so the ROCm release of llama.cpp (which needs glibc 2.38 or newer) starts inside it; with no ROCm libraries in the image the setup suggests the Vulkan build, which on an RX 6800 wrote about 25 tokens/s where ROCm outside Docker wrote about 100 with the same model and prompts (Qwen3.6-35B-A3B; 11.5 against 36 on Qwen3.8-27B). Inside the container llama.cpp downloads into `~/.llm-tulpa/llama-docker`, since the container's home is yours and its Vulkan build must not replace the ROCm or CUDA one a native backend keeps in `~/.llm-tulpa/llama`.
- A model that fails to load for lack of memory says so first: the model file's size against what the card has free (AMD cards, read from the kernel), and what to change — fewer layers on the GPU, a smaller quantization, a smaller context or KV cache — before the server's own last words.
- A dropdown is now as wide as its widest option from the start, so choosing a different value never resizes it and the list never cuts an option off, and one inside a popup opens toward the side with room instead of being clipped by the popup's edge.
- Export a chat — a share button in the chat header opens an "Export chat" popup: a format (PDF or Markdown), "Tool calls" (the tools the assistant ran, with their arguments and results, and job notices; off by default) and "Attachments", which is one of: **Not included** (default; a message that had some says how many were left out), **In the document** (images are shown in place, as pictures in the PDF and as embedded data in a Markdown file, and text files are printed; anything else, such as a binary or very large file, is left out and counted, and the result stays a single file) or **In a zip** (every attachment saved as a file in an `attachments/` folder in a `.zip` next to the document, with the images shown in a PDF too). The document holds the conversation with the times in the user's own timezone, and never the thinking traces, and the file is named after the chat. Message Markdown is kept in the PDF — headings, emphasis, lists, quotes, tables, code blocks and links — typeset with Typst using fonts compiled into the backend, so the same chat gives the same PDF on every machine and needs no browser or system fonts, inside Docker or out; those fonts cover Latin and Cyrillic, but not emoji or CJK, which appear as empty boxes. Attachments are set apart from the text in framed boxes tagged `IMAGE`, `FILE` or `ATTACHMENT` with the file name in the monospace font, and a dashed `NOT INCLUDED` box counts the ones left out. Words longer than a line are broken rather than running off the page. Backed by `GET /api/chats/export` (`chat_id`, `format` = `pdf`|`md`, `tools`, `attachments` = `none`|`embed`|`zip`); it reads only the caller's own chats and needs no model. It adds about 59 MB to the backend binary and about 2 minutes to a clean release build (Typst and its dependencies). A 2000-message chat (308 pages) exports to PDF in about 2 seconds in the release build, so it is one plain request, not a background task.
- Edit and delete messages — a delete button on every message and an edit button on the user's own. Delete removes that message and everything after it (a confirmation says how many), so the chat reads as it did just before it; it works on a reply too, which leaves the question before it unanswered. Edit puts the message's text and attachments back into the composer under a "Editing a message" banner with Cancel; sending deletes the original and everything after it, then sends the new text as an ordinary turn, so the thinking choice and attachments are the composer's as usual, and a refusal leaves the text in the composer. Both are offered only where nothing from that message onward is anything but plain conversation — a tool call, tool result or job notice there leaves its effects (a written file, a started job) unexplained — and refused (`409`, with the reason) in a sub-agent's chat, a messaging plugin's chat, and for messages the compaction summary has already folded in. Backed by `POST /api/chats/rewind` (`chat_id`, `message_id`), which checks and deletes in one transaction and clears the chat's last measured prompt size, since that described the longer history and drives compaction.
- Regenerate — a button next to the copy button on the chat's last reply (after a confirmation) has the model answer again and replaces that reply with the new one (`POST /api/agent/regenerate`, `chat_id` and the `message_id` of the reply). Only a plain final reply qualifies: the chat's newest message, from the assistant, with no tool calls, directly after a message of the user's and newer than the compaction boundary — anything with tools involved is left alone, since a tool's effects can't be replayed. The old reply is deleted only after the new one is stored, so a model that is down or fails leaves the chat as it was: the old reply leaves the screen while the model works, comes back if it fails, and the page says so and keeps the button. A sub-agent's chat and a messaging plugin's chat, whose reply has already gone out, can't be regenerated. A reply that asks for tools is then handled like any other turn. Anything else gets `409`.
- Search across all chats — a "Search chats" entry in the sidebar (also on the collapsed rail) opens the `/search` page, which finds chats by name and, with its "Messages" toggle (on by default, remembered per browser), by the text of their user and assistant messages. Results are grouped per chat, newest activity first, with up to three snippets each and the chat's total match count; clicking a chat opens it, clicking a snippet opens it and scrolls to and highlights that message, loading older pages first when needed. The query is in the address (`/search?q=…`), so Back from an opened chat returns to the same results. `%`, `_` and `\\` in the query match literally. Backed by `GET /api/chats/find` (`query`, `include_messages`, `limit`), which looks only at the chats the sidebar lists: the caller's own, not deleted, not a sub-agent's and not owned by a plugin.
- The tab icon follows the selected theme: the same leaf icon, on the theme's background color with its accent color, rebuilt in the browser whenever the theme changes. ### Changed
- The model is now told when to attach a file with `ui.attach_file`: a file the user has no other way to get (a script, document, image or archive made for them to take away without naming a place for it) or the result of a file they sent through the chat, but not a file written where they said to put it or an edit inside their own project. Before, the tool's description said to attach only when the user clearly wanted it and that most edits don't need it, so a file sent through the chat was rarely returned unless the user asked. The guidance is in the tool's description, in a system prompt rule, and in the note added to a message with attachments, so a coding session without attachments is unaffected.
- Every popup now shares one look and one implementation: a titled frame with a minimum size (380px wide, 120px tall), a body that spaces its rows evenly, and a Cancel / confirm row whose two buttons share the width. Rename and delete-confirmation popups, which were plain boxes without a title, get the same frame as the folder, model and search popups; context menus stay unframed. The popups live in `frontend/src/components/popups/`: the building blocks in `base/` (`Popup`, `PopupActions`, `ContextMenu`, `ConfirmPopup`, `InputPopup`, and the attachment preview's `WindowsPopup`), and thin ready-made ones next to them (`AssignFolderPopup`, `ChooseModelPopup`, `SearchMessagesPopup`, `NewChatPopup`, `NewFolderPopup`), each defined once and reused. A rename popup's Save is disabled while the name is blank, and saves it trimmed.
- Auto-confirm is now a per-user setting stored with the rest of the user's settings (`user_settings.auto_confirm`, saved with the Settings page's Save button) instead of a per-browser toggle, so it follows the user across browsers and the backend can honour it for sub-agents. A browser that had it on starts with it off.
- A finished job's notice now appears the moment the job ends, not together with the model's reply to it: `POST /api/agent/job_notices` persists the notices and returns them without calling the model, and the frontend then calls `POST /api/agent/continue` for the reply. It used to call the model itself and return the reply with the notices, so the notice only showed once the model had finished answering.
- The system prompt now includes explicit guidance to verify images before attaching them and to compile or otherwise test a code change rather than assuming it works.
- `ui.attach_file` tool description clarifies that files should be attached directly to replies rather than suggesting external links or file hosts.
- Theme picker layout refined: nested list container, responsive grid with min-width constraints, scrollbar styling, and a scrollable settings panel body.
- An unexpected HTTP status from Ollama now carries the response body through to whoever asked, instead of just the status code — `llm.read_image` against a model with no vision projector used to fail with only "ollama returned status 500", leaving the model to guess why; it now sees Ollama's own explanation ("image input is not supported - hint: if this is unexpected, you may need to provide the mmproj") directly.
- The system prompt asks for a concrete working state before each tool call — the specific deduction or question driving it, the exact detail expected back, and the next action once it arrives — rather than the vaguer "briefly say what you're about to do" framing, since thinking itself doesn't survive past the end of a turn. It also now treats the project's own build/compiler/type-checker as the way to resolve an uncertain API signature (write the best-guess call, run the checker, act on the diagnostic) rather than reading a dependency's source, and calls out that exploring a codebase has a natural stopping point: once the file(s) to change and roughly what to write are known, that's the signal to stop reading and make the edit. After 5 consecutive read-only tool calls with no edit or write in between, a notice is injected into the prompt naming the streak and repeating that guidance, so a long read-only stretch doesn't quietly continue past the point it stopped being useful. The compaction summary is now written into three explicit sections (established facts, completed changes, the current unsolved objective) and is told never to record an unexecuted intention or plan from a folded turn as if it were real progress — a real, observed cause of the model repeating an action it had only ever *planned* to take, not actually taken, in an earlier turn now folded out of view.
- `os.execute_command`'s foreground command timeout is lowered from 10 minutes to 90 seconds; the message shown when a command is killed for running past it now points at `os.start_job` for anything genuinely long-running and asks the model to first double-check the command wasn't just an accidental runaway.
- An assistant turn's reasoning trace is now replayed back into later turns' history (wrapped in `<think>...</think>` ahead of the message's own content, capped at 10,000 characters keeping the most recent end) instead of being dropped the moment the turn ends — plain text concatenation rather than a separate field, since not every backend a chat might be pointed at (an OpenAI-compatible proxy like `mtp-proxy`, for one) reliably forwards one. Aimed at a model re-deriving or re-exploring something it had already reasoned out and would otherwise appear to have simply forgotten a turn later.
- The model server is llama.cpp run by the backend itself, and the Ollama container in `llm/compose.yaml` is the optional `ollama` profile instead of the default.

### Fixed
- A chat could be left without a name when the model answered the naming prompt with nothing, which a small or heavily quantized model does: it is now named from the first words of its first message ("New chat" for an image sent alone).
- The greeting and the placeholder examples were written again on every save of the settings, even with the same name and timezone, so the model server did that work for nothing; they are now written again only when the name or the timezone really changes.
- The browser's cross-origin check listed `*` as the allowed request headers, which doesn't cover `Authorization` and which browsers are about to stop accepting (a console warning on every request); the backend now names `Authorization`, `Content-Type` and `Accept`.
- Pointing the setup wizard at a database that already has an account (an existing install) asked for a new account and failed with "That username is taken"; it now goes to the login page, with a note that the database already has an account.
- The home page showed "Thinking" for ever, with an uncaught error in the console, when the model server couldn't answer the greeting; it now shows the page without one. The Ollama tab's "could not reach Ollama" says where the address is set.
- A reply cut off by the token limit while the model was still reasoning (empty visible content, `done_reason: "length"`) was stored and shown as-is — an apparently blank turn, most often on models with long chains of thought (observed repeatedly with Qwen 3). This is now recognized as its own failure mode: the partial reasoning is kept as a message, and one automatic follow-up turn asks the model to answer based on what it had already worked out, with fresh budget. Separately, the per-request `num_predict` budget was being computed from an estimated character-to-token ratio that skewed conservative enough to often collapse to its floor on an ordinary prompt, cutting a reply short well before the real context ceiling; it's now anchored to Ollama's own reported token count from the previous turn (`chats.last_prompt_tokens`, reset after each compaction fold) instead of re-estimating from scratch every time, and the floor itself is raised to give a long reasoning trace enough room to actually finish. The nudge that asks the model to answer from its cut-off thoughts is a `notice` (the same muted, backend-written marker a finished-job notice uses) rather than a real chat message, so it doesn't render as something the user typed; compaction is checked against the full token count of that turn (prompt plus everything the model had already thought through), not just the prompt, so it can free room before the automatic follow-up if the conversation is already near the ceiling.
- Reopening a chat whose last tool call was cut short — the backend restarted while a command was running, or the page closed during it — re-ran that command automatically. A command that never exits (a dev server started in the foreground) then held the chat on "Thinking…" for the full ten-minute limit, every time it was opened. A call that the chat's permissions already allow and that was left unfinished is now recorded as interrupted, with a note to the model that it may have run only partly and was not repeated; a call waiting for the user's confirmation still waits. A second tool call for a chat that already has one running is refused, so a reload can't start the same command twice.
- The page overflowed horizontally at narrow window widths — the chat/home/folders panel (a flex item of the page row) had no `min-width: 0`, so it could not shrink below the min-content width of the chat header and composer footer (each a few hundred px of fixed-width controls). The page's `overflow: hidden` is still a scroll *area*, so focusing the composer made the browser scroll it into view — the view "drifting" sideways when typing, with the sidebar half cut off. The panels can now shrink, and the wide items in both bars (the header's model name, folder name and context gauge; the composer's hint text, "Thinking" label and thinking-mode selector) truncate with an ellipsis instead of holding their full width, so the bars fit a narrow window rather than spilling past it.
- Every model call re-evaluated the whole prompt once a chat passed 200 messages: `agent_history_len` (how many of a chat's most recent messages go into a turn) defaulted to 200, so from then on each new message pushed the oldest one out, the prompt changed from its first message onward, and llama.cpp could reuse only the system prompt and tool definitions from its cache — about two minutes of prompt processing per call at ~65k tokens instead of one to three seconds. Tool-heavy turns reach 200 messages long before compaction (which bounds history by tokens) fires. The default is now `2000`, so compaction is what limits a long chat; a setup that pins its own value in `settings.json` keeps it and should raise it (see the table in [`backend/README.md`](./backend/README.md)).
- A long chat could trigger history compaction every one to three turns, each time costing a full prompt re-evaluation (about 150 seconds at ~92k tokens). A compaction fold rewrites the summary at the very front of the prompt, which invalidates the whole cached prefix, and the fold's target for how much recent history to keep was so close to the trigger that each fold removed only one to four messages before the next one was due; it now keeps a much smaller tail (`KEEP_CHARS_PER_TOKEN` 1.2 → 0.6), so the next fold is tens of thousands of tokens of growth away.

### Removed
- The `mtp` compose profile, `llama-mtp` and `mtp-proxy` (`llm/mtp-proxy/`, `llm/start-mtp.sh`): the backend talks to llama-server directly and uses its MTP head through a launch profile, and `./start-docker.sh` no longer switches `ollama.url` between backends. `COMPOSE_PROFILES=mtp` in a root `.env` no longer selects anything.

## [0.1.5] - 2026-09-20
### Added
- Accounts and multi-user isolation — the app now signs in. The first account created is the **owner**; only the owner can add or remove other users (from a new in-app Users page), and there is no open self-registration. Every chat, setting, uploaded file, and plugin configuration is scoped to the user who owns it — a second user sees none of the owner's data, and a cross-user access attempt 404s. Sessions are JWTs (`Authorization: Bearer`, 30-day TTL, `bcrypt`-hashed passwords), with a TUI login page and a shared axios layer that attaches the token and signs out on an expired one. - First-run setup wizard — a 10-step carousel that walks a fresh install through language, timezone, the PostgreSQL connection, the owner account (with a live password-strength meter), the LLM provider, the model to chat with, a theme, and notifications. The backend no longer needs a database configured to start: with none, it comes up in setup mode serving only `/api/setup/*` + login, and the wizard's database step (`POST /api/setup/database`) connects, migrates, and swaps the live services in without a restart. Connection details and an auto-generated JWT secret persist to a JSON config file (`data/settings.json` next to the binary, on every platform); The database connection is read only from that file — never from environment variables or `.env` — and `GET /api/setup/status` pings it, so a missing or unreachable database makes the frontend redirect every page to the wizard (as does any API call answering 503); Under Docker the same file lives in a host folder, `backend/data/`, so it can be edited by hand.

A shared model picker (in the wizard's model step and the chat header's switcher) lists installed models with size/quant/estimated-memory requirements (`GET /api/llm/models`), and sets a chat's model (`POST /api/chats/model`; the model has to be installed). The owner can also browse Ollama's public library as JSON (`GET /api/llm/catalog`, parsed on the backend), pull a model or a Hugging Face GGUF (`hf.co/<user>/<repo>`) with live progress (`POST /api/llm/pull`), and import `.gguf` files already on disk — several at once, optionally paired with an `mmproj` for vision (each file's kind is read from its GGUF header, only projectors that fit the model are offered and a mismatched one is refused) — without downloading anything (`GET /api/llm/local_files`, `POST /api/llm/import`); pulls and imports run in the background and are watched at `GET /api/llm/tasks`.
- Graduated thinking-effort control — when the active model's own chat template supports a set of effort levels (e.g. `xhigh`/`medium`/`low`), the composer now offers them in a selector next to the existing thinking on/off toggle, and the chosen level is sent verbatim as `think` instead of a plain bool; the toggle itself still works exactly as before for any model. Which levels are offered is discovered live per composer mount from the model's own chat template (`GET /api/llm/thinking_capability` — a new endpoint that reads the template via Ollama's `/api/show` and extracts the exact strings the template's `reasoning_effort` check accepts, in the order it lists them), not hardcoded per model family and not cached anywhere: the active model can change without a restart, the call reads stored model metadata with no model load required, and a template with no recognizable thinking markers at all degrades to no control rather than one that would do nothing. - Media previews for file attachments — image, video, and audio files attached by id (including files the model attached to its own reply via `ui.attach_file`) render in the preview popup, and an image's small attachment chip shows a real thumbnail instead of a generic file icon. The download route needs the session token, which a media element can't send, so the bytes are fetched with it and shown from a `blob:` URL.
- Every backend setting now lives in `data/settings.json` (Ollama's address and context length, the bind address, the files folder, the background-jobs folder and log retention, SearXNG, the model folder, the database) with `settings.example.json`/`settings.docker.example.json` listing them all — the backend reads no environment variables or `.env` any more. `MODEL_FILE` in `llm/` is optional.
- The `mtp` compose profile (`llm/compose.yaml`) — an optional raw llama.cpp server build with Multi-Token Prediction speculative decoding (`llama-mtp`) plus a small Ollama-to-OpenAI wire-format translator sidecar (`mtp-proxy`), since Ollama 0.34.0 has no `--spec-type`/MTP flag at all and silently ignores the MTP draft-head tensors some of our GGUFs already carry. Whether MTP helps turns out to be genuinely task-dependent — a clean, short-prompt benchmark and real, conversation-depth usage through the actual chat API don't necessarily agree — so it's meant for occasional per-task A/B rather than day-to-day use: it's kept fully configured and buildable but out of a plain `docker compose up -d` behind a named compose profile, so it doesn't load a model into the same card as `ollama` at once. `llama-mtp`'s startup flags mirror the Ollama service's KV-cache quantization, flash-attention, context length, and mmproj pairing so a comparison doesn't also compare different settings; `ollama.url` in the backend's `settings.json` pointed at `:11435` is all it takes to switch.

Where the narrative summary gets regenerated from itself on every fold and can gradually compress away specific detail, key facts are only ever appended to, never rewritten: each fold makes a separate, focused extraction call (existing facts shown only as "don't repeat this" context, never fed back in for the model to re-derive), and merging the result into what's already stored is a deterministic Rust function, not a model rewrite. Shown to the model as a distinct "Key facts (durable...)" block ahead of the narrative summary once a chat has any.
- `extensions/launcher` — a minimal, always-on-top desktop input bar (egui/eframe) for starting a chat without opening the browser first: type a prompt, press Enter, and it opens the frontend with that prompt already filled in and sent (a new `?prompt=` query param on the home page picks it up, creates the chat, and navigates straight there). Its random placeholder text comes from the same `POST /api/prompts/input_examples` the frontend itself uses, with a built-in fallback if that call fails. Three built-in themes (`slate`/`paper`/`matcha`, the same colors as those frontend themes) via `LAUNCHER_THEME`. See `extensions/launcher/README.md` for configuration and build instructions.
- The system prompt now asks for a brief (1-2 sentence) note before each tool call — what's about to happen, why, and what result is expected — and a brief check afterward on whether the result matched, including partway through a long chain of tool calls in the same turn. Aimed at a real, observed failure mode: a long agentic session producing tool call after tool call with empty visible content and enormous hidden thinking traces, which is both hard to follow from outside and a sign the model isn't checking its own progress along the way.
- Background jobs — `os.start_job`, `os.job_output`, `os.job_kill` and `os.list_jobs`. Starting a long-running command (a dev server, a watcher, a big build) with `&` inside `os.execute_command` leaves the model with no defined way to see how it goes: the output goes nowhere it can find, nothing tells it when the process ends, and nothing stops it from ending its turn saying it'll "wait". A job instead gets an id and a log file the tool owns (`jobs_dir` in `settings.json`, default `~/.llm-tulpa/jobs`, stdout and stderr interleaved), a row in a new `jobs` table tracking `running`/`exited` (with its exit code)/`killed`/`lost` (the backend restarted while it ran), and a watcher that records how it ended. `os.start_job` waits a bounded time (default 3s, at most 30) for an early exit, so "failed immediately" versus "still running" is part of what the call returns rather than something guessed from a delay — a missing program or a port already in use shows its error in the same result. Every job belongs to the chat that started it; another chat's job looks like it doesn't exist. Approving a command word covers both `os.execute_command` and `os.start_job` (one shared permission bucket, like the storage tools' folder grants), and the same blocklist applies to both. A finished job's log is kept for `job_log_retention_days` (default 7, `0` keeps them all) and deleted by a sweep when the backend starts — not when the job ends, since the model and the user still need to read it afterwards; `os.job_output` then reports that the log was cleaned up. Everything platform-specific about running a job (shell selection, detaching into its own process group, killing a whole process tree) lives in one module, `services/process.rs`, written for Unix and Windows — the Windows side is only cross-compile-checked, not run.
- Job notices and push. When a background job ends on its own, the model finds out without polling: at the start of that chat's next turn a `notice` message ("Background job 3 (`npm run build`) finished successfully (exit code 0)...") is persisted after the newest message already stored and before the model's reply — never between a tool call and its result — and reaches the model as a user-role message. The UI shows it as a muted marker in the timeline, in the same place after a reload; the turn's response carries it (`ChatOut.notices`) so what's on screen and what's in the database agree. A `GET /api/events` Server-Sent Events stream tells connected frontends a job finished (it's the backend's one channel for anything it needs to push — every event is a `type` in the same stream, so a new kind of event is a new variant, not new plumbing — and each page holds a single shared connection, opened only while a component is listening), and when the chat has no turn running the frontend starts one itself (`POST /api/agent/job_notices`, which decides server-side whether there's anything to report and does nothing if not, so a stale or duplicate hint is harmless); an event that arrives mid-turn is deferred until the turn ends, not dropped. A job whose outcome the model already saw in a tool result isn't reported a second time, and a job it stopped with `os.job_kill` never is. The system prompt tells the model it will be notified, so it can carry on or end its turn instead of waiting.
- `storage.read_file` takes an `offset` (characters to skip from the start) and reports `total_chars` and `next_offset`, so a file past the 40,000-character cap can be read in order, part by part, with the same tool — instead of the model running out of ways to see the rest and reaching for `os.execute_command` to `sed`/`tail` it. The truncation marker in the content names the range shown and the offset to continue from, and a read past the end of the file says so.
- Three new themes — Ember, Twilight and Cinder, warm dark palettes (amber on near-black, muted gold on deep blue-black, cream on charcoal) added to the picker on Settings and Setup alongside Slate, Paper and Matcha. Each is the same three color tokens every theme is, so nothing else needed to change; text contrast against the background is 8.8:1 or better on all three.

### Changed
- A shell command word approved for `os.execute_command` is now approved for `os.start_job` too (and the other way round), because both draw on one shared permission bucket. An approval granted before this change lived in `os.execute_command`'s own bucket and is not carried over — that command word gets asked about once more in each chat that had it approved.
- The database schema was rebuilt and normalized to 3NF for the per-user model: a `users`/`user_settings` split replaces the old global settings singleton, `chats` and `files` are owned by a user, message images/file-ids and the old plugin columns are normalized into join/side tables, and a single centralized migration is versioned by a `schema_meta` sentinel and never wipes data. **Upgrading from 0.1.4 keeps everything**: the old tables are moved into a `legacy` schema and, when the owner account is created in the setup wizard, the chats, messages, attachments, tool calls, permission grants, plugin settings and settings are copied over for it (the old tables stay as a backup).

### Fixed
- `os.execute_command` returned stdout and stderr uncapped, so a single oversized command output stored as a chat message could blow the model's context window on the next turn — Ollama then silently truncated the oversized history down to fit (no error anywhere in the pipeline, and that path shipped with zero logging), which excluded nearly the entire actual conversation, so the model's very next reply looked like it had genuinely forgotten everything. Stdout and stderr are now each capped independently at 40,000 characters — the same cap-and-truncation-marker convention as `storage.read_file` — and the tool's own description tells the model the cap exists and how to work around it for genuinely large output (narrower searches, byte-bounded pipes rather than line-capped ones), since that's exactly the kind of thing the model needs to know to not re-trigger the same failure.
- The `Select` dropdown panel (the thinking-mode selector's container, but any `Select`) always opened downward, so a trigger near the bottom of the viewport — the chat composer is exactly that, and it's where this control lives — clipped the panel off-screen and made every option past the first unreachable. It now measures the actual space below the trigger when it opens (not at mount — the trigger's position can change between opens) and opens upward when there isn't enough room below and more room above.
- Ollama's prompt cache was failing to match on almost every turn — llama.cpp's own logs showed as little as 3 tokens of a 47,000+ token prompt matching anything cached, forcing a full reprocess of the entire conversation history instead of just what's actually new, and turning prefill deep into a conversation into most of a turn's wall time (tens of seconds, sometimes over a minute, dwarfing actual generation). Two independent causes, both in what gets sent as the prompt's very first tokens (where the cache's prefix match starts, so any change there invalidates everything after it, no matter how much of the rest is identical to the last call): the system prompt embedded a fresh to-the-second timestamp on every single call, and each tool's parameter schema serialized from a freshly built `HashMap`, whose randomized per-instance iteration order changed the schema's literal text on every call even with identical tool definitions. Fixed by moving the timestamp onto whichever message is newest each turn (the new user turn, or a tool result — content that was never going to be cached anyway) instead of the static system prompt, and by switching the tool-schema map to a `BTreeMap` for deterministic ordering. Live-verified against a 275,000-character stress conversation: steady-state turns now reuse 90%+ of the cached prefix and complete in ~4-5s instead of ~40-70s at the same real context depth.
- Compaction's "how much recent history to keep verbatim" budget assumed roughly 2 characters per token — reasonable for English prose, but this project's actual traffic is agentic and tool/code-heavy, which measures closer to 2.3 real characters per token. That left barely any margin below the trigger threshold: the kept, not-yet-summarized tail could sit right at the budget's ceiling, leaving almost nothing eligible to fold on a given pass, so compaction re-triggered on nearly every turn — each time regenerating the summary/facts and re-paying a full prompt-cache miss — instead of settling comfortably below the trigger for a while. Lowered the assumed ratio to give real headroom for this kind of content.
- The per-request generation cap (`num_predict`) was a flat number matching the full context window, with no accounting for how many tokens the prompt itself had already used. On a turn with an already-large prompt, Ollama believed it still had the full cap's worth of room to generate — a real one hit this exactly while writing a large tool call: generation ran into the actual context ceiling mid-JSON, which llama.cpp can't gracefully stop, so the truncated tool call failed to parse and the whole turn errored out with nothing applied. `num_predict` is now computed per request from the prompt's own estimated size (character-based, calibrated to this project's real code-heavy ratio, with a `saturating_sub` rather than a subtraction that could silently wrap into a nonsense cap on an unsigned overflow) plus the actual serialized size of whatever tools are attached, so it always reflects genuinely remaining room rather than a number that ignores how full the context already is.
- `os.execute_command` waited for its stdout/stderr pipes to reach EOF, which only happens once every process holding the write end has exited — including anything the command backgrounded with `&`, which inherits them. Starting a dev server that way (`python3 -m http.server 8899 &`, an obvious thing for an agent to do) made the call never return, with no timeout anywhere, so the chat sat on "thinking" indefinitely with nothing logged and no error. Output now goes to scratch files and only the shell's own exit is waited on: a backgrounded process returns immediately and keeps running (its later output goes to an already-unlinked file rather than a closed pipe, so it isn't killed by a broken-pipe error the next time it logs). A foreground command that genuinely never exits is now killed, with its whole process group, after 10 minutes, returning whatever it had printed plus a note saying so. The tool's description points the model at `os.start_job` (see Added) for anything long-running, and says a `&` command's own output isn't captured anywhere it can get back to.
- An agentic turn could stop dead on a model reply that did nothing: the model wrote its tool call out as text — inside its reasoning, typically ending in a stray `</parameter></function></tool_call>` — instead of actually calling the tool, so no call was parsed, nothing ran, and the turn ended on an empty reply. Such a reply is now thrown away and generated again (up to twice) instead of being stored; only the reply that's kept is saved, and the time shown covers every attempt. Recognizing it needs no per-model knowledge: the wrapper tags to look for are read from the active model's own chat template (`<tool_call>`/`</tool_call>` for Qwen, whatever another model's template names), the same discover-it-live way as its thinking-mode levels, and a model whose template has none is left alone. A reply with no answer and no tool call that wasn't cut off by the token limit gets one regeneration, since that can also be a stall — but only one, because an empty reply is sometimes exactly what was asked for. A reply cut off by the token limit is never regenerated (it would hit the same wall), and a real tool call is never second-guessed.
- Debian bookworm's own packaged `rustc`/`cargo` (baked into the backend image for `os.execute_command`'s own use) is old enough to reject current-edition crates outright. Now copied from the build stage's own toolchain instead of installed via `apt-get` — that stage already has a current, verified-working Rust (it just built `backend` with it), so this costs no extra download and can't drift out of sync with whatever actually built the image.

### Fixed
- `OLLAMA_CONTEXT_LENGTH` could silently disagree between the backend and Ollama itself, since each read its own separate `.env` file — a single oversized tool result could then exceed what Ollama could actually accept, entirely silently (no log on the backend side, no error surfaced in the UI). Now sourced from one root `.env` for both; an Ollama request failure is logged with its actual status/body, and a failed turn now shows a visible, dismissible error in the chat instead of the "thinking" indicator just disappearing.
- `web.request` returned an HTML response as raw markup rather than its actual readable content — now converted via `html2text` before the size cap applies; its description also now points at the baked-in Playwright for anything JS-rendered, interactive, or screenshot-worthy.
- `storage.list_directory` had no cap at all, so a large enough directory's listing alone could exceed the model's context budget in one call — now returns at most 200 entries per call (sorted by name), with an `offset` argument to page through the rest.
- `web.search_query`'s `bing` engine was returning results with nothing to do with the actual query (almost certainly Bing's own scraper-hostility blocking SearXNG's engine) — replaced with `yandex`.
- `os.execute_command`'s destructive-command blocklist matched `dd`/`mkfs` as a raw substring anywhere in the command text, so unrelated text merely containing e.g. "sed dd od" as a list of tool names got permanently blocked with nothing to approve. Now only matches them as an actual leading word of a shell statement.
- A `LazyList` (the chat sidebar, message history) could end up scrolled to the wrong position after loading — its `jumpToTop`/`jumpToBottom` didn't update the list's own internal scroll anchor, so the very next unrelated render could drag the scroll position back to a stale computed value.
- A browser notification fired with an empty body when a reply's content came back blank (e.g. the model exhausted its output budget before producing an answer).
