# Tools
How the model gets to actually do things — read/write files, inspect the machine it's running on, reach the web, and whatever else gets added here.

## How it works
Every tool implements the `Tool` trait ([`src/tools/base.rs`](./src/tools/base.rs)):

```rust
trait Tool: Send + Sync {
    fn function_name(&self) -> &str;
    fn description(&self) -> &str;
    fn required_properties(&self) -> Vec<PropertyInfo>;
    fn is_dangerous(&self, data: Value, scope: ResolvedScope) -> Result<ToolPermission, ToolSerializationError> { .. }
    fn shared_buckets(&self) -> &'static [SharedBucket] { &[] }
    async fn call_untyped(&self, data: Value, ctx: &ToolContext) -> Result<Value, ToolError>;
}
```

`function_name`/`description`/`required_properties` become the JSON schema the model server sees — the model decides whether and when to call a tool based on that text alone, so a vague description directly causes missed or wrong calls. `call_untyped` gets the model's raw arguments and returns raw JSON back. `ctx` (`ToolContext`) is what a tool may reach beyond its own arguments — the file store, the Ollama client, the background job store, the event bus, the sub-agent handle, and the id of the chat the call is happening in (so a tool never takes a chat id as a model-facing argument). Most tools ignore it; a field is added only when some tool actually needs it.

`is_dangerous` defaults to always-allowed. A tool that can actually change or expose something overrides it to return `Denied { reason, escalation }` unless the chat already has a matching grant — `escalation` (a `ScopeGrant`) is what lets the user approve a whole scope at once ("allow everything under `~/project`", "allow every request to `api.example.com`") instead of confirming every single call. A tool's scope is a `ResolvedScope`: its own grant (per `(chat_id, tool_name)`, for facts nothing else cares about — `web.request`'s per-host permission, say) plus whatever **shared buckets** it opted into via `shared_buckets()`. A folder grant is checked where the path really is, symlinks resolved (`storage::real_location`; a file is resolved before its folder is taken, and a link whose target doesn't exist yet is followed by hand), and is offered under that real location: a symlink inside a granted folder that leads out of it doesn't carry the grant, and a folder granted through a symlinked path covers the place it names. A shared bucket is cross-tool: every `storage.*` tool that reads files declares `SharedBucket::StorageRead`, so approving `storage.read_file` for a folder also covers `storage.list_directory`/`storage.find_files`/etc. for that same folder without a second prompt — granting write or delete access stays separate (`SharedBucket::StorageWrite`/`StorageDelete`), each is its own independent level. `SharedBucket::ShellCommands` works the same way across tools that run a command line: approving a command word for `os.execute_command` also covers it for `os.start_job`. Grants persist via [`PermissionStore`](./src/services/permission_store.rs), keyed by tool name for a tool's own bucket or by a fixed `GLOBAL.*` key per shared bucket (see `SharedBucket::db_key`).

**A call cut short is never run again on its own.** A call the chat's grants already allow runs the moment the model asks for it, so one that is still unresolved when nothing is executing — the backend restarted mid-command — was interrupted. A turn starting on the chat (or a job waking it) records it as a failed `tool` message, before the new message telling the model it may have run only partly and was not repeated, instead of re-running it. A call waiting for the user's confirmation is left pending, as are the calls queued behind it (the calls before it that need no permission have already run). While a call is executing, a second one for the same chat is refused (409) and nothing is reported as pending, so a reload or second tab can't start the same command twice. (A chat's run is the only thing that runs its tools; see *The agent and its turn runner* below.)

**A chat without tools.** `chats.tools_enabled` (the user's `use_tools` setting is its default for new chats; `POST /api/chats/tools` changes one chat) sends the model no tool definitions: `Turn` empties the tool list, the built-in system prompt is the short `default_system_prompt_without_tools` (a custom one is sent as written), the fold and pinned-message headers leave out the `chat.*` references, and no notes request is made. The tool definitions are about 9,000 tokens of every request, so a window under about 32k with them on spends most of itself on them: at 16k the system prompt and tools alone were 11,100 tokens, past the compaction trigger, and nothing could be folded to get under it.

## The agent and its turn runner
`facade/agent.rs` is the thin public `Agent` (what the routes and the messaging plugins call); the work is in private components under `facade/agent/`, each owning its own state, built in dependency order in `Agent::new`. A component never holds `Agent`.

| Component | Does |
|---|---|
| `prompts.rs` | every fixed text the model is sent: the system prompt, notes added to messages, the summarizer's and notes' instructions, headers of the blocks after a fold |
| `History` | builds what the model is sent from a chat's stored rows: the system message (rules, key facts, the user's pinned messages, summary, notes), one-line stubs for cleared tool results, thinking at its cap. `load` reads the stores, `build` is a pure function of what was loaded, and its bytes are pinned by tests: the model server's cached prompt is matched against them |
| `ModelCall` | the chat's provider and launch profile, call parameters and context window, the turn's claim on the model server, and the policy for a reply that can't be used (a tool call written as text, an empty reply, one cut off while thinking) |
| `Compaction` | at 70% of the window: clear old tool results, ask the model for its notes while the prompt is still cached, and fold into a summary and key facts only if that wasn't enough; back-off after a failed fold. The key facts are bounded (60 entries, 6,000 characters, the first 10 kept) and merged by plain text comparison: a fact already said is skipped, a fuller one replaces its part. A message's size counts its tool-call arguments and template overhead as well as its text |
| `ToolCalls` | pending calls, permissions and stored scopes, running one call, calls cut short by a restart, which chats have a call running; a tool result over a quarter of the window is stored cut |
| `Notices` | turns finished background jobs and sub-agent results into `notice` messages |
| `Turn` | one step: build the request, ask the model (a stop drops the call in flight), store the reply with its tool calls, compact when needed. `make_room` checks the size of the request about to be sent (last measured prompt plus what was added since) so a large tool result can't push it over the window |
| `TurnRunner` | the loop, one run per chat (below) |

**A run.** `POST /api/agent/turn` stores the prompt and starts a run in the background; a second one on a chat that has a run is refused (409), so two tabs can't run a turn twice and a closed tab stops nothing. The run loops steps: a model call, then the tool calls it asked for, then the model again, until it answers, the user stops it, the step limit is reached or a tool needs permission. **Permission never waits:** a call needing a permission the user hasn't given ends the run in `waiting_for_permission` (read back from the stored chat); `POST /api/agent/answer` (`permanent`, `only_now` or `deny` per pending call) starts the next run. With the user's auto-confirm on, the grants are made and the run goes on. `POST /api/agent/stop` drops the model call in flight and stores nothing of it; a tool already running finishes. `POST /api/agent/regenerate` runs through the same runner. A messaging plugin's agent has no tools and calls `Agent::reply`, a single step with no run.

**State and events.** `GET /api/agent/turn?chat_id=` returns `idle`, `running` (since when, when the current model call started, tokens generated so far, the step and the step limit, the tool that is running) or `waiting_for_permission` (with the pending calls and what each needs), and how the last run ended. `GET /api/agent/runs` lists the caller's chats that have a run going on, each with that same state (and the `parent_chat_id` of the chat that started it, for a sub-agent). A chat also keeps how its last run ended, `unseen_end`, until its owner opens it: the backend sets it when a run ends (not for a stop), clears it when the next run starts, `GET /api/chats` returns it and `POST /api/chats/seen` clears it and sends `chat_seen` (creating, renaming and deleting a chat send `chat_created`, `chat_renamed` and `chat_deleted` the same way, and a rewind or the reply a regenerate replaces sends `messages_removed` with the ids that went), which the user's other open pages take as "drop the mark". `GET /api/live` carries `run_started` (with the `parent_chat_id` of a sub-agent's run), `messages_changed` (read what is newer than the last message you have: `GET /api/chats/messages?after_id=`), `tool_started`, `turn_progress` and `run_ended` (answered, failed with its reason and HTTP status, stopped, step limit, waiting for permission, plus the run's start and tokens). A page that is reloaded reads the state once and follows the events, so "thinking for 1m 30s, N tokens" counts from the real start.

**Step limit.** The user's `max_turn_steps` (none by default), counted over the whole turn: a wait for permission and the answer that continues it are one turn. On the last allowed step the newest message of the request gets a note that the reply is the last for now and must be plain text (what is done, what is left); a tool call in that reply is dropped from the stored message and its text kept; the run ends as `step_limit`. The note's wording matters: a first version that asked for a "conclusion" was ignored in 6 of 6 live runs, the current one was obeyed in 6 of 6.

**Jobs wake the chat.** A finished job or sub-agent starts a run on its chat by itself, with no browser open. A chat with a run reports the job at its next step; a chat waiting for permission keeps the notice until the user answers (a new message would supersede the pending call); messaging-plugin and sub-agent chats are not woken. After a run ends the runner looks once more, for a job that finished during its last model call.

**Sub-agents** run on the same runner with the sub-agent policy: nobody can be asked, so what a call's escalation offers is granted with auto-confirm and the call is refused without it, the run ends at `llm.return_agent`, and it has at most 100 model calls.

**Known limits.** The tool definitions are about 9,000 tokens of every request and the system prompt more; a window under about 32k with tools on spends most of itself on them (see *A chat without tools*). Details dropped by a fold are gone from the prompt: the summary header tells the model to read a value again instead of reconstructing it, but a model can still fill a gap with a plausible value (measured: 29 of 60 hashes in a final file, in one run before the header existed; the same task with the header gave 60 of 60 in one run, which is a hint, not a measurement).

## Adding a tool
[`src/tools/temperature.rs`](./src/tools/temperature.rs) is the smallest real example:

```rust
#[derive(Deserialize, ToolParams)]
struct TemperatureArgs {
    #[tool(description = "The city or place to get the temperature for.")]
    location: String,
}

#[async_trait]
impl Tool for TemperatureTool {
    fn function_name(&self) -> &str { "get_temperature" }
    fn description(&self) -> &str { "Get the current temperature for a given location." }
    fn required_properties(&self) -> Vec<PropertyInfo> { TemperatureArgs::tool_properties() }

    async fn call_untyped(&self, data: Value) -> Result<Value, ToolError> {
        let args: TemperatureArgs = serde_json::from_value(data)?;
        // .. do the thing, return JSON
    }
}
```

1. Write the args struct. `#[derive(ToolParams)]` (from the [`tool_derive`](./tool_derive) crate) reads each field's type plus its `#[tool(description = "...")]` attribute and generates the schema for you — `Option<T>` fields become optional automatically, everything else is required. There's no enum/oneOf support — a field with a fixed set of allowed values (e.g. an HTTP method) stays a plain `String`, with the allowed values spelled out in its description, and gets validated at call time instead.
2. Implement `Tool`. Only override `is_dangerous` if the tool can actually change or expose something that matters. If it shares a concern an existing shared bucket already covers (reading/writing/deleting under a folder, say), declare that bucket instead of managing its own separate grant — see `storage.rs`'s tools for the pattern, or `web/request.rs` for a tool combining its own bucket (per-host permission) with a shared one.
3. Register it. A one-off tool gets added straight to `tool_list` in [`main.rs`](./src/main.rs). A *domain* of related tools (see below) gets its own `collect()` instead.

### Domains
`os`, `storage`, `web`, `files`, `ui`, and `llm` are domains — a `tools/<domain>.rs` file (e.g. [`tools/storage.rs`](./src/tools/storage.rs)) next to a `tools/<domain>/` folder (e.g. [`tools/storage/`](./src/tools/storage/)) with one file per tool, each domain exposing `pub fn collect() -> Vec<Box<dyn Tool>>` (registered in `main.rs` via `tool_list.extend(tools::<domain>::collect())`). Function names are dot-namespaced: `storage.read_file`, not just `read_file`. Put a new tool in an existing domain if it shares that domain's concerns (e.g. another filesystem op belongs in `storage`, not standalone) — shared logic (like `storage`'s path-scoping helpers) lives in the domain's own `<domain>.rs`, not copy-pasted per tool.

## Current tools
These are the built-in domains, registered directly in `main.rs`. A plugin can also contribute its own tools (registered live when the plugin is enabled, removed when disabled) — see [PLUGINS.md](./PLUGINS.md), e.g. `coding.get_signatures`.

### `get_temperature`
Fake/hardcoded — the original proof-of-concept tool, kept around as the minimal example above. Not dangerous.

### `os` — info about, and some control over, the machine running the backend
Mostly read-only and ungated. The tools that run commands (`os.execute_command`, `os.start_job`) and `os.env_write` genuinely change or expose something and are scoped narrowly — see the table.

| Tool | What it does | Permission |
|---|---|---|
| `os.get_date` | The actual current date/time (UTC, plus this backend's own local clock) — mostly a fallback for a precise/machine-readable timestamp, since the current date is already appended to the newest message on every turn (see `History` in `facade/agent/history.rs`, and `SYSTEM_PROMPT`'s matching rule, in `facade/agent/prompts.rs`) so the model doesn't assume a stale one from training. | none |
| `os.get_hardware` | CPU model, GPU model + VRAM, system RAM, OS name. GPU fields come back `null` if nothing supported was detected. | none |
| `os.get_disk_space` | Every mounted disk/volume, `df`-style: filesystem, mount point, size, used, available. | none |
| `os.get_process_list` | Running processes, sorted by CPU usage (highest first): PID, name, CPU%, memory, status. Can filter to one PID or cap the result count. | none |
| `os.get_network_info` | Network interfaces and their IPv4/IPv6/MAC addresses, and whether each is up or down. | none |
| `os.cpu_usage` | Current CPU usage %, logical CPU count, and 1/5/15-minute load averages. | none |
| `os.get_user_info` | Username, home directory, and process executable path of the user running the backend. | none |
| `os.env_read` | Reads the environment the commands this backend runs see (its own variables plus any set with `os.env_write`) — all of them, or one by key. | none |
| `os.env_write` | Sets an environment variable for the commands this backend runs from then on (`os.execute_command`, `os.start_job`), until it restarts — kept in `services::process`, not in the backend's own environment, which can't be changed safely while other threads read it. Refuses a short blocklist outright: obviously sensitive names (`PATH`, `*_TOKEN`, `*_KEY`, etc.) and those that make the shell or the dynamic linker run code in every later command (`LD_*`, `DYLD_*`, `BASH_ENV`, `ENV`, `PROMPT_COMMAND`, ...). | approve once per exact variable name, reused for any future value written to it — a different variable still needs its own approval |
| `os.execute_command` | Runs a shell command and returns stdout/stderr/exit code (each capped independently at 40,000 characters, truncated with a marker past that — same convention as `storage.read_file`). Output goes to scratch files rather than pipes and only the shell's own exit is waited on, so a command that backgrounds something (`cmd &`, e.g. a dev server) returns immediately and the background process keeps running undisturbed; a command still running in the foreground after 90 seconds is killed along with everything it started (its process group), and whatever it printed by then is returned. Anything long-running belongs in `os.start_job` instead, which the description says — inside this backend's own container if running under Docker (see the repo root's `compose.yaml`), directly on the host otherwise; `description()` reflects whichever is actually true at runtime. Under Docker the container permanently ships python3 (+pip/venv), nodejs (+npm), go, rustc (+cargo), build-essential, git, jq, unzip/zip, curl, wget, poppler-utils, ripgrep, fd, tree, sqlite3, docx2txt, gnumeric, and Playwright + a real headless Chromium (`DISPLAY` is set too, so a non-headless launch shows up as a real window on the host's own screen) — the model is told this list directly and is free to `apt-get`/`pip`/`npm`/`cargo`/`go get` install anything else on top (a scoped, passwordless `sudo` covers just `apt-get`/`apt`/`dpkg`, spliced in transparently via shell aliases so it applies wherever those are actually invoked in a command, not just as its first word); anything installed this way only lasts for that container instance, unlike the baked-in list. Blocks `dd`/`mkfs` as a command anywhere in the line, and `rm -rf /`/`> /dev/sd*` as a substring, outright regardless of approval. | approve once per command word (e.g. `python`), reused for that word with any arguments. Every command the line would run needs its own approval, not just the first: each statement's first word after `;`, `&&`, `\|\|`, `\|`, `&` or a newline, inside `$( )` and backticks, after `then`/`do`, and after a wrapper like `sudo` or `xargs` (which counts too); quoted text, comments, heredoc bodies and `VAR=value` prefixes are not commands (`command_words` in `tools/os/shell.rs`). One prompt offers every missing command of the line at once. Shares `SharedBucket::ShellCommands` with `os.start_job` |
| `os.start_job` | Starts a shell command as a background job and returns right away with a job id and the path of its log. Waits up to `wait_seconds` (default 3, at most 30) for it to finish by itself, so a command that fails immediately (a missing program, a port already in use) shows its error in the same result. The job keeps running on its own, and a message appears in the chat when it ends (see *Background jobs* below). Same access, blocklist and per-command approval as `os.execute_command`. | approve once per command word, shared with `os.execute_command` via `SharedBucket::ShellCommands` |
| `os.job_output` | A job's status (`running`, `exited` with its exit code, `killed`, or `lost` if the backend restarted while it ran) plus the end of its output — stdout and stderr combined, in order — at most `tail_lines` lines (default 100) and 40,000 characters. Works the same while it's running and after it finishes. Only jobs started in this chat. | none — reads the output of a command that was already approved |
| `os.job_kill` | Stops a running job and everything it started. A command job marked `lost` (the backend restarted while it ran) is stopped too while its process still runs — only once the process with the recorded pid is shown to be the job's own (it started when the job did, `process::started_around`), since after a reboot that number can belong to anything. Fails, saying what state it's in, if it already finished. Only jobs started in this chat. | none — never broader than starting it was |
| `os.list_jobs` | Every job started in this chat, oldest first: id, kind (`process` or `agent`), command, status, exit code, log path. For finding a job's id again or seeing what's still running. | none |

**Background jobs.** A job is either a shell command (`JobKind::Process`) or a sub-agent (`JobKind::Agent`, see *Sub-agents* under `llm`): a row in `jobs` ([`JobStore`](./src/services/job_store.rs)) plus a log file (`jobs_dir` in `settings.json`, default `~/.llm-tulpa/jobs/<id>.log`, stdout and stderr interleaved) — output goes to a file rather than a pipe, so nothing waits on the process and a job that keeps running keeps writing undisturbed. A tokio task watches each process and records how it ended. Everything platform-specific about running one (`sh -c` vs `cmd /C`, detaching into its own process group, killing a whole process tree) lives in [`services/process.rs`](./src/services/process.rs). A job whose backend restarted while it ran is marked `lost` on the next start. The log of a finished job is kept for `job_log_retention_days` (default 7, `0` = forever) and removed by a sweep at startup — not when the job ends, since the model and the user need to read it afterwards; `os.job_output` then says the log was cleaned up.

When a job ends on its own, the model has to find out without polling and without depending on it remembering to check:
- the watcher publishes a `job_finished` event on the [`EventBus`](./src/services/event_bus.rs), which `GET /api/live` streams to the frontend as Server-Sent Events — each signed-in user's stream carries only the events about chats that user owns, since the bus itself is shared by everyone (one-way, server to client — each event is only a hint, the data is always read back through the normal API). Every event is an unnamed SSE message carrying its `type`, so adding an event is adding a `ServerEvent` variant (routes publish through `AppState::events`, tools through `ToolContext::events`, services through the bus handed to their constructor) plus one line in the frontend's `ServerEvent` union; a page holds one shared connection however many components subscribe, opened only while something is listening;
- at the start of every step of a chat's run, `Notices` claims every finished-but-unreported job (atomically, so two callers can't both report one) and persists a `notice` message per job — after the newest message already stored and before the model's reply, so it can never land between a tool call and its result. A `notice` reaches the model as a `user`-role message, the UI renders it as a muted marker, and it comes back in the same place after a reload;
- when the event arrives and the chat has no run and no tool call waiting for permission, the backend starts a run itself (`TurnRunner::wake`): it stores the notices and asks the model, with no browser open, and the run goes on until the model answers, a stop, a step limit or a tool that needs permission. A chat that has a run reports the job at that run's next step. A chat waiting for permission keeps the notice until the user answers: a new message supersedes unresolved tool calls, so waking it would drop the pending one. Messaging-plugin chats and sub-agent chats are not woken (nobody would read the reply). A job that ends during the last model call of a run is reported at the next step of a run on that chat, not on its own.

A job whose outcome the model has already seen through a tool result (`os.start_job` returning it finished, `os.job_output` on a finished job, `os.job_kill`) is not reported again.


### `storage` — reading and writing files
Every tool here is scoped per-folder, and read/write/delete are three independent shared permission levels — approving `storage.read_file` under a folder also covers every other read tool there (`list_directory`, `find_files`, `detect_file_type`), but implies nothing about write or delete access to the same folder. File-targeting tools (`read_file`, `write_file`, `replace_str`, `delete_file`, `detect_file_type`) scope to the file's *containing folder*; directory-targeting tools scope to the directory itself.

| Tool | What it does | Level |
|---|---|---|
| `storage.read_file` | Reads a file as text (up to 64 MB: it is read whole to find lines and offsets, so a larger one is refused with a pointer to `head`/`tail`/`grep`; `llm.read_image` stops at 32 MB and `ui.attach_file` at the 500 MB upload limit for the same reason). At most 40,000 characters come back per call (the file itself is untouched); `max_chars` asks for fewer, down to 1, so the model can preview a file or one long line before paying for more. The result says whether more follows (`truncated`), how long the file is (`total_chars`, `total_lines`) and where to pick up (`next_offset`, in characters from the start of the file), which is passed back as `offset` to read the next part. `start_line`/`end_line` (from 1, inclusive, not combinable with `offset`) read a range of whole lines instead: a range cut by the limit names `next_start_line`, and a first line that alone is over the limit comes back cut with a `next_offset` to go on from. An `offset` or line past the end says so instead of returning nothing. | read |
| `storage.list_directory` | Lists a directory's immediate contents — name, type, size, modified time, read-only — like `ls -lsh`. Returns at most 200 entries per call, sorted by name; an `offset` argument pages through the rest, and a `note` field says how many are left when truncated. | read |
| `storage.find_files` | Searches a directory tree by filename substring, file-content substring, or both. A subfolder it can't open is skipped (only the folder asked for has to open), symlinked folders aren't walked into, and files over 16 MB aren't read for a content search. | read |
| `storage.detect_file_type` | Identifies what a file actually is by sniffing its first bytes (magic numbers) rather than trusting its name — the right first call on something of unknown format, e.g. right after `web.download_file`. Returns a general kind (image/video/audio/archive/doc/font/text) plus a MIME type when recognized. | read |
| `storage.write_file` | Overwrites a file's entire contents, or appends to the end. Creates the file if needed. | write |
| `storage.replace_str` | Swaps one exact, unique snippet of a file's current text for new text — a precise edit, preferred over `write_file` for changing part of an existing file. | write |
| `storage.create_directory` | Creates a directory, including missing parents (`mkdir -p`). | write |
| `storage.delete_file` | Deletes a single file. | delete |
| `storage.delete_directory` | Deletes a directory and everything in it, recursively (`rm -rf`). | delete |

### `web` — reaching outside this machine
Every tool here is scoped per-host (the exact hostname, no wildcard/subdomain matching — `example.com` and `api.example.com` need separate approvals) rather than per-folder. Runs with whatever network access this backend's own environment has (e.g. `network_mode: host` under the repo's Docker setup), so approving a host is a real decision, not a formality.

| Tool | What it does | Permission |
|---|---|---|
| `web.download_file` | Downloads a URL straight to a file on disk and returns status code/content type/bytes written — the body itself is never returned inline, so this is the tool for anything binary or large. Follow up with `storage.detect_file_type` and `storage.read_file`. Written to disk as it arrives (never held in memory whole), given up after 60 seconds without data, and removed again if it fails partway. Redirects are handled like `web.request`'s: only within the same host. Needs both a host grant and a folder grant (shares `storage.write_file`'s `SharedBucket::StorageWrite` for the destination). | host approved once, reused |
| `web.request` | Makes an HTTP request (GET/HEAD/POST/PUT/PATCH/DELETE) and returns status/content-type/body inline (UTF-8, lossily decoded, capped at `max_response_bytes` — default 50,000, hard-capped at 500,000). An HTML response is converted to its extracted readable text (via `html2text`) before the cap applies, not raw markup — but this is a plain GET, nothing here runs the page's JavaScript, so a JS-rendered page comes back as a near-empty shell; use the baked-in Playwright (`os.execute_command`) for that, or for anything needing interaction or a screenshot. For reading an API response or small page *now*; use `download_file` for anything binary or too large to read inline. A request has 120 seconds in all, and at most 8 MB of a response is read whatever the cap. A redirect is followed only while it stays on the same host; one to another host comes back as the answer with `redirected_to`, so reaching that host takes its own request and its own approval (a host is approved by name, and a redirect to `localhost` must not ride on it). Two independent per-host levels: approving GET/HEAD covers GET/HEAD there from then on; approving any one of POST/PUT/PATCH/DELETE covers all four there from then on, *and* GET/HEAD too (write implies read, not the reverse). | host approved once per level, reused |
| `web.search_query` | Runs a web search against a local SearXNG instance (see the repo root's `searxng/`) and returns `{title, url, snippet}` results. For anything the model wouldn't know from training alone — current events, a specific library/product, recent docs. | none |

`web.search_query` needs the `searxng`/`searxng-nginx` services from the repo root's `compose.yaml` running (`searxng_url` in `data/settings.json`, default `http://localhost:8090` — the rate-limiting sidecar's port, not searxng's own 8080) — see `searxng/settings.yml` for which search engines are enabled (currently Google, Yandex, and DuckDuckGo — Bing was dropped after its SearXNG engine started returning results with nothing to do with the actual query) and `searxng/nginx.conf` for the rate limit in front of them (calls are throttled at the container level, not in this backend's own code, so a burst of searches can't hammer the underlying engines). Both services run `network_mode: host`, same as `backend` itself — a bridge-networked SearXNG can't reach the outside internet at all when outbound traffic depends on host-level VPN/proxy routing.

### `files` — files already attached to this chat, referenced by id
As opposed to `storage.*`, which takes arbitrary real filesystem paths the model names itself.

| Tool | What it does | Permission |
|---|---|---|
| `files.get_attached_file` | Given a file id from an attached-files note on a message, makes a snapshot copy and returns its path and name — read the path with `storage.read_file` (or `storage.detect_file_type` first) to actually see its content. Refuses (same error as "doesn't exist") for a file id not attached to this chat. | shares `storage.read_file`'s `SharedBucket::StorageRead` |

### `chat` — the chat's own history, for when a message has scrolled out of the context window
The model only ever sees a window of the chat's most recent messages (plus a summary of what came before), so anything older is reachable by id through this pair instead: list it, then fetch the full text of the ids it wants. Both are scoped to the chat the call is happening in — no chat id is ever a model-facing argument — and both are ungated, reading a chat the model is already inside.

| Tool | What it does |
|---|---|
| `chat.list_messages` | The chat's `user`/`assistant` messages, newest first: id, who wrote it, when, and a whitespace-collapsed 120-character snippet of the content. `role` filters to one writer; `limit` (default 50, at most 200) and `offset` (from the newest end) paginate; the result carries `total` and a `next_offset` to continue. Tool results and notices are never listed, and the assistant messages that only carry tool calls are left out unless `include_tool_calls` is set — in an agentic chat they are nearly all of the assistant's rows and would bury the user's messages and the actual replies. |
| `chat.get_messages` | The full text of the ids `chat.list_messages` returned, any mix of user and assistant, oldest first. An id that isn't a `user`/`assistant` message of this chat — foreign, deleted, or a tool result/notice — comes back in `missing` instead of failing the call. `ids` (like `limit` and `offset` of `chat.list_messages`) also takes numbers written as strings, via `tools/lenient.rs`, since models do that. |
| `chat.write_notes` | Saves the model's own working notes for the chat (`notes`, the whole text, replacing the previous ones; at most 8,000 characters, a longer text is refused rather than cut). A write goes to `chats.notes_pending` and joins the system message at the next compaction, not at once: the system message is the front of every request, so changing it makes the model server read the whole conversation again, and the text the model passed stays in view in its own tool call until then. From there the notes go out after the compaction summary on every request, and a fold never shortens them — the summary deliberately keeps findings and drops plans, so this is where a plan survives. Right before a fold or a clearing pass the backend also asks the model, as an extra unstored message on the live prompt (with the chat's own thinking setting, so the model server's cached prefix still serves it), to rewrite its notes; a reply that is empty, `UNCHANGED`, a tool call or over the limit leaves them as they were, and pending notes become the prompt's notes either way. The request is only made while at least 16,000 tokens of the window are free (a model that thinks first needs room to write them), so on a window of about 53k or less it is skipped and a plan survives a fold only if the model wrote it with the tool; an empty `notes` clears them. Stored in `chats.notes`. Needs no permission. |

### `ui` — making the frontend show the user something
| Tool | What it does | Permission |
|---|---|---|
| `ui.attach_file` | Snapshots a file from a real path and attaches it to the model's own reply, the same way a user-attached file would show up — not to *this* tool's own (usually content-empty) tool-calling message, but to whichever message turns out to be the turn's actual final, non-tool-calling reply (`History` in `facade/agent/history.rs` resolves this by scanning back through the turn's own tool calls for `ui.attach_file` results once the turn knows a reply won't call anything else). The model is told to attach a file when the user has no other way to get it — a script, image or archive made for them to take away without naming a place for it, or the result of a file they sent through the chat — and not a file it put where the user said, or an edit inside the user's own project; that guidance lives in this tool's description, in a `SYSTEM_PROMPT` rule, and in the note `with_attached_files_note` adds to a message that has attachments. | shares `storage.read_file`'s `SharedBucket::StorageRead` |

### `llm` — tools that make their own calls to the model, or start another agent
| Tool | What it does | Permission |
|---|---|---|
| `llm.read_image` | Looks at an image file by path and answers a given prompt about it (or gives a general description if none is given) — a one-shot, tool-free call straight to the model server, not a full agent turn. For an image found or pointed to via a path; an image already visible inline in the conversation needs no tool at all (an address, or a path that can't be read, fails with that reminder, since a model that was shown an image can still name a path or URL of its own invention). | shares `storage.read_file`'s `SharedBucket::StorageRead` |
| `llm.run_agent` | Hands a task to a sub-agent and returns at once with a job id (and the sub-chat's id). The sub-agent works in a chat of its own with the full toolset minus `llm.run_agent` and the four background-job tools, and reports one result; its work never enters the calling chat. The description tells the model this saves context, not time. See *Sub-agents* below. | none — the sub-agent starts with the calling chat's grants and can be given no more |
| `llm.return_agent` | Only offered inside a sub-agent's chat: hands the result back and ends the run. Its result is exactly its `output` argument, which the run driver reads as the sub-agent's answer; an empty `output` is an error so the run carries on. | none |

**Sub-agents.** `llm.run_agent` starts a run through `ToolContext::subagents`, a [`SubagentHandle`](./src/tools/subagent.rs) bound to the `Agent` after it is constructed — `Agent` holds the `ToolContext`, so a direct reference would be a cycle; the handle keeps only a `Weak`. The run itself is [`Agent::start_subagent`](./src/facade/agent/subagent_run.rs):
- it creates a chat with `parent_chat_id` set (same user, model and folder as the caller; hidden from the chat and folder lists, reachable from its parent only, and soft-deleted with it), copies the caller's tool grants into it, and records the run as a **job of kind `agent`** — a `jobs` row whose `command` is the prompt and whose log file holds the result — so it reports back exactly as a finished command does (see *Background jobs*): `job_finished` event, a `notice` message in the calling chat carrying the result (cut to a share of the context window, `INLINED_RESULT_FRACTION`; the log keeps all of it), `lost` if the backend restarted, `os.job_kill` aborting it;
- it runs on the same turn runner as an ordinary chat (`TurnRunner::run_subagent`, with the sub-agent policy) — model call, run the pending tools, continue — with at most 100 model calls. It ends when the sub-agent calls `llm.return_agent` (its `output` is the result), stops calling tools (its last message is the result), or runs out of calls (reported as not finished). One case is handled apart: if an `llm.return_agent` call was refused (a missing `output`, say) and the sub-agent then just stops, that last message is usually only "I'll call it now" — so it gets one reminder turn, and if it still doesn't return, the run is reported as not finished with the message it wrote when it tried and its last message;
- sub-agents run one at a time (`Agent::subagent_slot`): they share one model, and two taking turns would each throw away the other's cached prompt on every call;
- nobody can answer a permission prompt in a sub-agent's chat, so a call the copied grants don't cover is refused, with a tool result that says so — unless the user has **auto-confirm** on (a per-user setting), in which case the escalation is granted to the sub-agent's chat only, as an ordinary chat's auto-confirm does. Grants never flow back to the calling chat;
- delegation is one level deep: `tools::subagent::available_to` decides what a chat is shown (`llm.run_agent` and the job tools only outside a sub-agent, `llm.return_agent` only inside one), and the same check refuses a call to a hidden tool. A sub-agent has no job tools because it ends when it stops calling tools — one that started a job and wrote "waiting for it" would hand that sentence back as its result. A sub-agent chat's system prompt gets an extra section (`subagent_system_prompt`) after the usual one.
