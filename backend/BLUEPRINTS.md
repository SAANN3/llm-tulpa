# Blueprint documents

The blueprint API stores user-owned workflow drafts. The backend owns the list, metadata and
versioned JSON files; an editor sends a complete workflow when saving the graph. This API does
not execute graphs, create chats, start schedules or publish blueprint SSE events.

## Storage and ownership

`BlueprintStore` owns the `blueprints` table: id, user_id, name, revision, workflow_path,
schedule, created_at and updated_at. `blueprints_dir` in settings.json defaults to
`~/.llm-tulpa/blueprints`. A document lives at:

```text
<blueprints_dir>/<user_id>/<blueprint_id>/workflow-<revision>.json
```

The path is generated by the server, stored relative to the configured root and never accepted
from an API caller. The configured root may itself be a symlink; user/blueprint directories and
referenced documents may not redirect through symlinks. All access filters by the authenticated
user. A missing or another user's blueprint returns 404, including to the owner account.

`revision` advances on every save, including metadata-only saves. `workflow_path` can therefore
point at an earlier revision: changing the name or schedule does not write a document. The
workflow's `schema_version` is a separate version of the document format (currently 1).

Mutations lock the blueprint row and compare `expected_revision`. A stale edit/delete returns
409. A workflow save writes a temporary file and renames it to its new revision before committing
the row. A write failure preserves the previous row and file. Old revisions are retained; a failed
or ambiguous database commit may leave an unreferenced file. There is no revision-history API or
orphan sweep in this batch. Deleting a blueprint removes its row and then attempts directory
cleanup, logging cleanup failures. Deleting a user cascades database rows; filesystem cleanup of
that user's blueprint directory is not implemented yet.

Schedule configuration is stored in the row, outside the workflow:

```json
{"type":"manual"}
{"type":"interval","seconds":300}
{"type":"daily","time":"09:00","timezone":"Asia/Yekaterinburg"}
```

Daily times use HH:MM and a validated IANA timezone. These are stored settings, not an active
scheduler. Runtime queue state and ticks will not rewrite workflow documents.

## API

All endpoints require the normal bearer authentication. There are no owner-only blueprint operations.

| Method | Path | Request / result |
|---|---|---|
| GET | `/api/blueprints` | `offset=0`, `limit=20` (1–100), `q`, `sort=created` or `updated`; returns `items`, `total`, `offset`, `limit` |
| POST | `/api/blueprints` | `{name, schedule?, workflow}`; returns metadata with revision 1 and status 201 |
| GET | `/api/blueprints/{id}` | Returns `{blueprint: metadata, workflow}` |
| PUT | `/api/blueprints/{id}` | `{expected_revision, name, schedule, workflow?}`; returns updated metadata |
| DELETE | `/api/blueprints/{id}?expected_revision=N` | Returns 204 |

Lists are newest first, with descending id as a stable tie-breaker. Search is a case-sensitive
literal substring of the name, including literal `%` and `_`. Lists read only the metadata table.
Names need 1–160 non-whitespace/bounded characters; leading/trailing whitespace is trimmed.
Omitting or sending null for `workflow` on PUT preserves the file. PUT requires name and schedule
explicitly, so an edit cannot accidentally reset the schedule through a default.

Request-shape/deserialization errors use axum's JSON rejection responses. Semantic draft/settings
errors return 400; missing resources return 404 and revision conflicts 409. File/database failures
return 500 without exposing stored paths or database errors.

## Typed document

A minimal editable draft is `{"schema_version":1,"nodes":[],"edges":[]}`. Example:

```json
{
  "name": "Project summary",
  "schedule": {"type":"interval","seconds":21600},
  "workflow": {
    "schema_version": 1,
    "nodes": [
      {"id":"start","name":"Start","position":{"x":0,"y":0},"kind":{"type":"entry"}},
      {
        "id":"summary","name":"Summarize","position":{"x":300,"y":0},
        "kind": {
          "type":"agent",
          "model":{"type":"user_default"},
          "prompt":{"source":"literal","value":"Summarize my project notes."},
          "tools":{"mode":"whitelist","names":["storage.read_file"]},
          "reuse_chat":false,"write_notes":false,"write_memory":false
        }
      },
      {
        "id":"result","name":"Result","position":{"x":600,"y":0},
        "kind":{"type":"return","values":{"text":{"source":"output","node_id":"summary","port":"text"}}}
      }
    ],
    "edges": [
      {"id":"begin","from":"start","port":"out","to":"summary"},
      {"id":"finish","from":"summary","port":"out","to":"result"}
    ]
  }
}
```

`NodeKind` is a serde tagged enum, not an arbitrary JSON config. Kinds in schema version 1:

| Kind | Configuration |
|---|---|
| `entry` | No timer; the execution entry point |
| `generate` | model, prompt, optional think |
| `agent` | model, prompt, optional system_prompt/think, tools, reuse_chat, write_notes, write_memory |
| `tool` | name, arguments keyed by the tool's argument names |
| `sleep` | seconds as an input binding |
| `if` | left, operator, right |
| `switch` | value, cases (`port`, literal `value`); `default` is reserved |
| `format` | template, arguments |
| `return` | named result values |
| `plugin` | plugin_name, plugin_subname, node_type, positive version, arguments |

Model choice is `{type:"user_default"}` or `{type:"model", id, launch_profile_id?}`.
Thinking reuses the existing `ThinkChoice` (boolean or effort string); tools reuse `ToolMode`
(`whitelist` or `blacklist`) plus names. Other model parameters will be specified with execution.
Agent chat reuse, notes writing and global-memory writing default to false. Compaction has no
switch in this document. These flags describe the intended execution policy; this API only stores
them. A system-prompt override does not imply changing or deleting the user's global memory.

Inputs are another typed enum:

- `{source:"literal", value: ...}`: null, boolean, integer, number, string, list or object.
- `{source:"output", node_id, port, path?: [...]}`: another node's output, with optional field names
  and array indices, e.g. `["items", 0, "text"]`.
- `{source:"array", items: [input, ...]}` and `{source:"object", fields: {name: input}}`: nested
  structures whose individual values can be bound independently.

Edges control execution; bindings control data dependencies. The order in the edges array defines
the order of edges leaving the same port. This batch preserves that order but does not traverse it.
There are no variable, arithmetic or loop nodes yet.

Draft validation rejects unknown schema versions, duplicate/invalid IDs, dangling node references,
invalid settings and oversized documents (1 MiB, 1000 nodes, 4000 edges; binding depth at most 32).
It deliberately does not require a complete executable graph. Tools/models/plugins need not be
currently installed to save a draft. Port types, reachability, cycles, argument compatibility,
permission handling and executable readiness belong to the next validation/execution batches.
A `plugin` node here is a stored identity and typed bindings, not plugin registration or a new RPC
contract; neither SDK has changed in this batch.
