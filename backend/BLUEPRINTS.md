# Blueprint documents

The blueprint API stores user-owned workflow drafts. The backend owns the list, metadata and
versioned JSON files; an editor sends a complete workflow when saving the graph. Manual runs execute the basic control/data nodes and publish user-scoped SSE events.
Agent execution and schedule ticking are not implemented yet.

## Storage and ownership

`BlueprintStore` owns the `blueprints` table: id, user_id, name, revision, workflow_path,
schedule, created_at and updated_at. `blueprints_dir` in settings.json defaults to
`~/.llm-tulpa/blueprints`. A document lives at:

```text
<blueprints_dir>/<user_id>/<blueprint_id>/workflow-<revision>.json
```

The path is generated by the server, stored relative to the configured root and never accepted
from an API caller. The configured root may itself be a symlink; user/blueprint directories and
referenced documents may not redirect through symlinks. All access filters by the authenticated
user. A missing or another user's blueprint returns 404, including to the owner account.

`revision` advances on every save, including metadata-only saves. `workflow_path` can therefore
point at an earlier revision: changing the name or schedule does not write a document. The
workflow's `schema_version` is a separate version of the document format (currently 1).

Mutations lock the blueprint row and compare `expected_revision`. A stale edit/delete returns
409. A workflow save writes a temporary file and renames it to its new revision before committing
the row. A write failure preserves the previous row and file. Old revisions are retained; a failed
or ambiguous database commit may leave an unreferenced file. There is no revision-history API or
orphan sweep in this batch. Deleting a blueprint removes its row and then attempts directory
cleanup, logging cleanup failures. Deleting a user cascades database rows; filesystem cleanup of
that user's blueprint directory is not implemented yet.

Schedule configuration is stored in the row, outside the workflow:

```json
{"type":"manual"}
{"type":"interval","seconds":300}
{"type":"daily","time":"09:00","timezone":"Asia/Yekaterinburg"}
```

Daily times use HH:MM and a validated IANA timezone. These are stored settings, not an active
scheduler. Runtime queue state and ticks will not rewrite workflow documents.

## API

All endpoints require the normal bearer authentication. There are no owner-only blueprint operations.

| Method | Path | Request / result |
|---|---|---|
| GET | `/api/blueprints` | `offset=0`, `limit=20` (1–100), `q`, `sort=created` or `updated`; returns `items`, `total`, `offset`, `limit` |
| POST | `/api/blueprints` | `{name, schedule?, workflow}`; returns metadata with revision 1 and status 201 |
| GET | `/api/blueprints/{id}` | Returns `{blueprint: metadata, workflow}` |
| PUT | `/api/blueprints/{id}` | `{expected_revision, name, schedule, workflow?}`; returns updated metadata |
| DELETE | `/api/blueprints/{id}?expected_revision=N` | Returns 204 |

Lists are newest first, with descending id as a stable tie-breaker. Search is a case-sensitive
literal substring of the name, including literal `%` and `_`. Lists read only the metadata table.
Names need 1–160 non-whitespace/bounded characters; leading/trailing whitespace is trimmed.
Omitting or sending null for `workflow` on PUT preserves the file. PUT requires name and schedule
explicitly, so an edit cannot accidentally reset the schedule through a default.

Request-shape/deserialization errors use axum's JSON rejection responses. Semantic draft/settings
errors return 400; missing resources return 404 and revision conflicts 409. File/database failures
return 500 without exposing stored paths or database errors.

## Typed document

A minimal editable draft is `{"schema_version":1,"nodes":[],"edges":[]}`. Example:

```json
{
  "name": "Project summary",
  "schedule": {"type":"interval","seconds":21600},
  "workflow": {
    "schema_version": 1,
    "nodes": [
      {"id":"start","name":"Start","position":{"x":0,"y":0},"kind":{"type":"entry"}},
      {
        "id":"summary","name":"Summarize","position":{"x":300,"y":0},
        "kind": {
          "type":"agent",
          "model":{"type":"user_default"},
          "prompt":{"source":"literal","value":"Summarize my project notes."},
          "tools":{"mode":"whitelist","names":["storage.read_file"]},
          "reuse_chat":false,"write_notes":false,"write_memory":false
        }
      },
      {
        "id":"result","name":"Result","position":{"x":600,"y":0},
        "kind":{"type":"return","values":{"text":{"source":"output","node_id":"summary","port":"text"}}}
      }
    ],
    "edges": [
      {"id":"begin","from":"start","port":"out","to":"summary"},
      {"id":"finish","from":"summary","port":"out","to":"result"}
    ]
  }
}
```

`NodeKind` is a serde tagged enum, not an arbitrary JSON config. Kinds in schema version 1:

| Kind | Configuration |
|---|---|
| `entry` | No timer; the execution entry point |
| `generate` | model, prompt, optional think |
| `agent` | model, prompt, optional system_prompt/think, tools, reuse_chat, write_notes, write_memory |
| `tool` | name, arguments keyed by the tool's argument names, require_confirmation (default false) |
| `sleep` | seconds as an input binding |
| `if` | left, operator, right |
| `switch` | value, cases (`port`, literal `value`); `default` is reserved |
| `format` | template, arguments |
| `return` | named result values |
| `plugin` | plugin_name, plugin_subname, node_type, positive version, arguments |

Model choice is `{type:"user_default"}` or `{type:"model", id, launch_profile_id?}`.
Thinking reuses the existing `ThinkChoice` (boolean or effort string); tools reuse `ToolMode`
(`whitelist` or `blacklist`) plus names. Other model parameters will be specified with execution.
Agent chat reuse, notes writing and global-memory writing default to false. Compaction has no
switch in this document. These flags describe the intended execution policy; this API only stores
them. A system-prompt override does not imply changing or deleting the user's global memory.

Inputs are another typed enum:

- `{source:"literal", value: ...}`: null, boolean, integer, number, string, list or object.
- `{source:"output", node_id, port, path?: [...]}`: another node's output, with optional field names
  and array indices, e.g. `["items", 0, "text"]`.
- `{source:"array", items: [input, ...]}` and `{source:"object", fields: {name: input}}`: nested
  structures whose individual values can be bound independently.

Edges control execution; bindings control data dependencies. The order in the edges array defines
the order of edges leaving the same port. Execution traverses that order depth-first.
There are no variable, arithmetic or loop nodes yet.

Draft validation rejects unknown schema versions, duplicate/invalid IDs, dangling node references,
invalid settings and oversized documents (1 MiB, 1000 nodes, 4000 edges; binding depth at most 32).
It deliberately does not require a complete executable graph. Tools/models/plugins need not be
currently installed to save a draft. Static readiness is checked separately by the validation API below. Permission handling and
execution remain separate from saving and validating drafts.
A `plugin` node here is a stored identity and typed bindings, not plugin registration or a new RPC
contract; neither SDK has changed in this batch.

## Catalog and static validation

`GET /api/blueprints/catalog` returns the built-in node kinds, their control/data ports and data
value types. Switch case ports come from the saved configuration. Plugin nodes are not included: there is no plugin-node registration contract
yet. Saving such a draft is allowed, but validation reports `plugin_node_unavailable`.

Tools use the existing `GET /api/chats/available_tools`, not a blueprint-specific tool list. Each
entry contains `name`, `description`, and `properties` (the existing recursive `PropertyInfo`
contract used by tools and plugin settings). This catalog includes the user's currently published
global and private tools. A tool's publication is independent of chat/default whitelist selection.

`POST /api/blueprints/validate` accepts `{workflow}` without saving or executing it. The authenticated
user determines tool visibility and the default model. The result is `{valid, diagnostics}`.
Each diagnostic has `severity` (`error`/`warning`), nullable `node_id`, `field`, `code`, and `message`.
Field paths are relative to the node, except `edges[index]` and document-wide fields. Malformed
JSON is rejected by axum; a well-shaped but invalid graph returns HTTP 200 with `valid: false`.
Database failures remain HTTP errors. Structural errors stop deeper validation; readiness checks
collect multiple diagnostics.

Checks cover one entry, reachability, control ports, cycles, multiple incoming edges, data output
ports and availability, required/unknown arguments, recursive input types, registered models,
launch-profile ownership by model, and agent tool selection. An unavailable whitelist tool is an
error; a stale blacklist exclusion is a warning. No provider calls, model loading, permission
approval or tool execution happen during validation. Model registration is checked, not remote
provider health or existence of the model's files. Execution must check dependencies and permissions
again and must validate actual values before calling tools.

Control edges use ordered, depth-first sequential branches. A leaf (including Return) finishes its
branch; pending sibling branches still follow. Earlier unconditional branches can supply values to
later ones. A value produced only on one If/Switch outcome is not guaranteed available after that
conditional branch. Empty conditional outcomes finish without producing branch-specific values.
Multiple incoming edges and cycles are rejected until explicit Merge/Join/loop semantics exist.

Generate, Agent and Format publish a `text` string. Tool publishes `result`, whose schema is unknown:
the Tool interface declares argument schemas only. A binding to that output gets a
`runtime_type_check` warning, including when selecting a field/index. `valid: true` with that warning
means no statically known error, not a proof of runtime type safety. No implicit string/number/boolean
coercions happen. Integers are accepted where a number is required. Open object schemas accept
arbitrary keys; declared object fields are recursively checked.

Numeric ordering compares numbers; Contains compares strings. Equal/NotEqual and Switch require
compatible operand types. Sleep requires a nonnegative numeric duration (dynamic values still need
runtime range checks). Format uses named `{argument}` placeholders and `{{`/`}}` for literal braces.
Every placeholder requires an argument binding. Bindings retain their types; rendering their values
as text is explicit in Format: strings are used directly, other values render as JSON.


## Manual runs and queue

Each user has one sequential queue shared by all of their blueprints. Only one run per user
is active; different users can run independently. A start
validates the saved revision and stores an immutable workflow snapshot in `blueprint_runs`, owned
by `BlueprintStore`. Later edits affect future starts only. The runner executes Entry, Sleep, If,
Switch, Format, Return, Tool and Generate; starting a graph with Agent or Plugin returns 400.
Static validation can still describe those draft nodes without an executor.

| Method | Path | Request / result |
|---|---|---|
| POST | `/api/blueprints/{id}/runs` | `{expected_revision}`; 202 with queued run summary |
| GET | `/api/blueprints/{id}/runs` | `offset=0`, `limit=20` (1–50); `{items,total,offset,limit}`, newest first |
| GET | `/api/blueprints/{id}/runs/{run_id}` | `{run,workflow,state}` with snapshot and per-node outputs/status/error |
| GET | `/api/blueprints/queue` | `{running,queued}`; queued items in execution order |
| PUT | `/api/blueprints/queue` | `{run_ids:[...]}` containing every currently queued id once; returns queue |
| DELETE | `/api/blueprints/queue` | `{cancelled:N}`; cancels waiting runs, preserving history and current execution |
| POST | `/api/blueprints/queue/stop` | 202 `{run_id}` (null if idle); stops current run, preserving waiting runs |

Reordering sends the full desired order, so moving an item up/down is one atomic operation.
Missing, duplicated, foreign or already-started ids return 409 without changing the queue. Queue
membership is checked under the same user-row lock used when claiming a run. Deleting a
blueprint with running or queued work returns 409. Stop its active run if needed and clear
waiting work through the shared queue endpoint; clearing affects every queued blueprint of that user.

Run statuses: `queued`, `running`, `waiting_for_permission`, `stopping`, `completed`, `failed`, `cancelled`, `interrupted`.
Node statuses: `pending`, `running`, `waiting_for_permission`, `completed`, `failed`, `skipped`, `cancelled`, `interrupted`.
A node error fails its run and cancels the remaining nodes; the next queued run may start.
Sleep is cancellable. Return ends its branch, leaving ordered sibling branches to execute.
Unselected If/Switch branches are skipped. Numeric comparison preserves integer precision;
there is no implicit string/number conversion. Input resolution and formatted text are bounded
at 1 MiB per node, and persisted run state at 4 MiB, to bound expansion through references.

The runtime assumes one backend process per database. At startup, unfinished active runs become
`interrupted`; their actions are never replayed. Persisted queued snapshots resume in order.
A database error during execution stops that user's queue worker rather than risking replay; a backend
restart recovers the unfinished run and resumes the waiting queue. Schedules remain stored
configuration: this batch does not produce timer ticks.

The existing `/api/live` stream carries one `ServerEvent::Blueprint` wrapper containing a typed
`BlueprintEvent`. Its JSON is `{"type":"blueprint","event":{"type":"queue_changed","user_id":1}}`
or an inner `run_changed` event. Both carry `user_id` and are filtered to their owner before
delivery, without an ownership DB lookup per event. Run events also include `blueprint_id`,
`run_id`, status, current node, changed node/status and progress. They are refresh hints, not a replay log; clients fetch queue/run state
on reconnect. Node outputs are available through the run endpoint, not broadcast.

Progress reports completed/skipped node counts, total and percent. Untaken branches are excluded
from the total once the condition is evaluated, so the estimate can change during execution.
It measures node count, not elapsed time; a long Sleep and a Format each count once. Total and
percent are nullable for future executors whose remaining work cannot be counted. There are no
loop or merge nodes in the current executor.


## Tool nodes

Tool nodes resolve their bindings, validate the resulting values against the current user's tool
schema and use the ordinary agent tool pipeline: permission scopes, owner restrictions, plugin
hooks, tool context and recorded call/result messages. The workflow executor does not start a
parent model turn; a tool that itself uses a model or starts a sub-agent keeps that behavior. The output
port `result` contains the tool's JSON result as a typed workflow value; references can select its
fields/array elements. A failed or refused call fails the node/run. Results larger than 1 MiB fail
the node; execution does not retry actions whose outcome might already have taken effect.

`require_confirmation` defaults to false. Placing the call in the workflow authorizes the normal
auto-confirm scope grants for that call, independently of the ordinary chat auto-confirm setting.
Hard refusals (including owner-only tool restrictions) remain refusals. With
`require_confirmation: true`, an offered grant pauses the run and occupies the user's active
queue slot. Other users' queues continue independently. A tool already allowed by the context's
grants needs no extra prompt.

Each run lazily creates one service chat when its first Tool node executes. It uses the user's
current default registered model/profile at that point; creation fails clearly when no model is
registered. This binding supplies tools that need a model, but running an ordinary file tool does
not load or query it. The chat is hidden from the normal chat list and search. Its `chat_id` is
included in the run detail for auditing, files and jobs. Runs do not inherit permission grants
from earlier runs. Service chats do not automatically wake an agent when a background job finishes.
A tool explicitly starting a background job returns that job; the job's lifecycle remains managed
by the existing job tools and is not the lifetime of the blueprint node.

`GET /api/blueprints/{id}/runs/{run_id}` includes `state.pending_tool` (null unless waiting):
`request_id`, `node_id`, the existing `AgentToolCall` view (`name`, `arguments`, `permission`),
and a nullable `answer`. Answer with:

```http
POST /api/blueprints/{id}/runs/{run_id}/answer
Content-Type: application/json

{"request_id":"the currently pending id","allowance":"only_now"}
```

The response is 202. The accepted allowances are the existing `only_now`, `permanent` and `deny`.
Permanent grants last within this run's chat; only-now grants affect this invocation only. Calls
needing several scope facts may publish another pending request after an answer. Deny fails the
node without calling the tool. Missing/foreign runs return 404; stale, already answered or stopped
requests return 409. After answering, fetch the current run state or react to BlueprintEvent hints.
After a restart, permission waits become interrupted with the other unfinished active runs; they
are not replayed.

Stop cancels Sleep and permission waits promptly. As with ordinary agent tools, a tool that has
already started finishes before the run is reported cancelled; completed external/file actions
are not rolled back. No subsequent node starts after the stop.

## Generate execution

A Generate node makes one chat completion with its resolved string `prompt` as a user message,
without history, implicit system instructions or tools. Its `text` output contains only the response
content; reasoning is not included. Empty text remains a valid string. A structured tool call in the
response fails the node and does not execute anything.

`model: {"type":"user_default"}` resolves the user's current model and launch profile at execution.
An explicit `{"type":"model","id":N,"launch_profile_id":P}` uses that registered model and profile;
a missing model/profile or a profile belonging to another model fails. Omitting the explicit profile
uses the model's default launch profile. Sampling follows the user's existing preset for that model,
and `think` is passed through, including named effort levels. Launch, context length and sampling
are prepared by the same `LaunchFacade::call_params` method used by ordinary agent turns. The existing
provider claim protects the call from model switching. No service chat is created for Generate.

Stop cancels preparation, waiting for the provider and the completion itself, releases the claim,
and prevents later nodes from running. Provider errors fail the node without automatic retries;
the user's queue continues. Resolved inputs and output text have the usual 1 MiB limit, and the
persisted run state is limited to 4 MiB.
