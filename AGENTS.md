# For AI coding agents working in this repo

llm-tulpa is a local-first LLM chat agent with real tool-calling: Rust/axum backend, React/TS frontend, Postgres, Ollama for inference, everything Docker-packaged. See [`README.md`](./README.md) for the user-facing overview — this file is about working *on* the codebase itself. It is written for an agent that has never seen this repo: everything below either explains itself or points at a file that does.

Where things live: `backend/` (Rust; `src/routes` HTTP handlers, `src/services` stores and integrations, `src/tools` what the model can call, `src/plugins` messaging integrations), `frontend/` (React + TypeScript, Vite; `src/api` one file per backend endpoint, `src/components`, `src/pages`, `src/context`, `src/hooks`), `llm/` (the Ollama container), `postgres/` and `searxng/` (their containers), `compose.yaml` (the whole stack).

## Running it
```bash
HOST_UID=$(id -u) HOST_GID=$(id -g "$(whoami)") docker compose up -d --build
```
`HOST_UID`/`HOST_GID` matter: the backend container runs as that exact user (not root), so files `storage.*` tools write on the host keep the real user's ownership, and a scoped `sudo` for package installs is baked into the image for that same uid. After changing backend or frontend code, rebuild just that service rather than the whole stack: `docker compose up -d --build backend` (or `frontend`). Backend/frontend can also run directly without Docker — `cargo run` / `npm run dev` — see their own `README.md`s for configuration (the backend's is a JSON file, not env vars — next paragraph).

The backend reads **no** environment variables or `.env` — every one of its settings lives in `backend/data/settings.json` (`backend/data/settings.docker.example.json` lists them; `start-docker.sh` seeds it on a fresh checkout; see `backend/README.md`). Two `.env` files can still feed Docker Compose, and their scope is a real, easy-to-hit gotcha: the root `.env` is read by the root `compose.yaml` **and** by the included `llm/compose.yaml`, while `llm/.env` is read only by the latter. So anything both services need (`MODEL_DIR`: Ollama's model mount and the backend's `/models` mount; `OLLAMA_CONTEXT_LENGTH`) has to live in the root `.env`; Ollama-only settings (`MODEL_FILE`, the KV-cache quantization opt-in) can sit in either — see `compose.yaml`'s and `llm/compose.yaml`'s own comments. `ollama.context_length` in `settings.json` and `OLLAMA_CONTEXT_LENGTH` for Ollama must be kept equal by hand.

## Architecture notes worth knowing before you dig in
- **Multi-user, owner-gated.** Every DB-backed route is behind JWT auth (`routes/auth/`'s `require_auth` middleware + `AuthUser` extractor — it re-reads the user on every request, so a deleted user's or demoted owner's token stops working at once); handlers thread `user.id` and gate cross-user access via `chat_store.owned_chat`. The first account is the `owner` (the database allows at most one); owner-only handlers (users, plugins, pulling/importing models) take `OwnerUser` instead of `AuthUser`. `/api/auth/login` and `/api/setup/*` are the only unauthenticated routes, and `setup/database` closes itself once a database is configured.
- **Start-without-a-DB.** `AppState.services` is an `Arc<RwLock<Option<AppServices>>>` — `None` until a database is configured. `main.rs` reads the DB connection **only** from the JSON config file (`config.rs`) — deliberately no env/`.env` path; without it (or if it can't connect) the backend starts in setup mode and the wizard's `/api/setup/database` calls `services::bootstrap` (through `AppState::configure`, serialized so plugin loops can't start twice) and swaps the services in live. Handlers reach the stores through `state.services().await?` (503 when unconfigured). `GET /api/setup/status` pings the DB, and the frontend routes to `/setup` whenever it reports `configured: false` (or any API call returns 503).
- **One centralized migration.** `services/migrate.rs` owns the whole 3NF schema, versioned by `schema_meta.version`. A future version is a data-preserving `if current < N { ALTER … }` step in the same transaction plus a `SCHEMA_VERSION` bump — never a wipe; a database newer than the build is refused. The one-time upgrade from the single-user release moves its tables into a `legacy` schema and `adopt_legacy_data` copies them to the owner when that account is created. SeaORM entities are private to each store (a store needing another's data goes through that store's methods, or a read-only projection entity).
- **Providers/models live in the DB and every chat is bound to one.** `services/model_store.rs` owns `llm_providers`/`llm_models`; `chats.model_id` is NOT NULL and `user_settings.active_model_id` is the user's default (a chat starts with it, else the first registered model, else creation 409s). `OllamaService` holds no model — every `chat`/`generate`/`thinking_capability` call takes one, resolved from the chat (agent turns, `ToolContext.model` for tools) or from `SettingsStore::effective_model` (one-shot prompts). `services/model_library.rs` (in `AppState`, no database needed) owns the ollama.com catalog (parsed into JSON on the backend), the `.gguf` files under `model_dir`, and the background pull/import tasks behind `/api/llm/{catalog,local_files,pull,import,tasks}`; `AppState::require_installed_model` keeps a chat or default from being bound to a model Ollama doesn't have.

## Verify before claiming something works
This codebase has a strong, established live-verification habit — don't skip it:
- A backend change: a temporary `#[cfg(test)] mod temp_verify` block, run with `cargo test --bin backend` against the real (already-running) Postgres, deleted once it passes. Not a permanent test suite — a throwaway check for this one change.
- A frontend change: actually drive it (Playwright against the real running dev server, or the deployed container) rather than asserting from reading the code. Screenshot and look at it for anything visual.
- A tool description change: consider whether the model would actually see and act on it correctly — test with a real prompt through `/agent/chat` if the change is behavior-affecting, not just cosmetic.
Several real, non-obvious bugs in this project were only ever caught this way, not by review.

## Working agreement — how to behave, before any code rules
- **Do what was asked; surface the rest.** If you see a worthwhile extra change, propose it in one or two lines instead of doing it. If the task has a real design fork, give the options with a recommendation and let the user choose before building the large part. Never re-ask something the user already decided.
- **Report faithfully.** Say what you verified and what you only assumed. Do not call a multi-place edit "done" without re-checking every place. If a check fails or was skipped, say so with the output.
- **Attribute correctly.** Code written by someone else is described as theirs ("the branch does X"), never as your own work ("I converted…"). When you only reviewed, say nothing was edited.
- **Git.** Do not commit, push, rebase, reset, or delete branches unless asked. Do not edit another person's branch in place — create your own branch off it. When the user wants a large change reviewable, split it into commits by theme (mechanical renames, styling, behavior, backend wiring, data layer, docs…), stage one theme at a time, show it, and commit only after the user says so. A file that mixes themes gets staged in parts (build the intermediate content and stage that) — never dump 100+ files into one review. Commit subjects look like `type(scope): summary` in lower case. Never add attribution lines (see Git below).
- **Leave the user's running environment alone.** Do not restart, stop, or reconfigure their containers, databases, ports, volumes or `.env` files unless asked. For verification start throwaway containers on different ports (`docker run --rm`, e.g. Postgres on 55432, Ollama on 11435), and stop and delete them afterwards. If you must move or delete one of their config files, keep a backup outside the repo, verify the effective result is unchanged (`docker compose config` before and after), and say where the backup is.
- **When the user points at a mistake, look for its siblings.** If they flag a pattern (a style, an anti-pattern, a wrong assumption), search the *whole* change for the same pattern, in files already reviewed and files not yet written, and fix them all before showing anything again.
- **Shell traps.** Never `pkill -f`/`pgrep -f` with a pattern that also appears in your own command line — it kills your own shell. Find a process by its port (`ss -ltnp | grep :3103`) and kill that pid, in a separate command. Do not chain `sleep` with other commands.

## Code conventions (all languages)
- **Match the file you are editing** — indentation, semicolons, quotes, function style. The frontend is deliberately not perfectly uniform; never reformat unrelated code or run a formatter over whole files.
- **Frontend file and folder names are kebab-case** (`chat-entry.tsx`, `use-messages.ts`, `allow-scope.ts`); inside a file a component is PascalCase and a hook is `useX`. Use only ASCII in identifiers and file names — look-alike letters from other alphabets (a Cyrillic `е` in place of a Latin `t` happened) produce names that look right and import wrong. No byte-order marks. Check with `grep -rnP '[^\x00-\x7F]' <paths>` and `head -c3 file | xxd`.
- **Comments explain WHY**, not what: races, workarounds, protocol quirks, and why an obvious alternative was rejected. When refactoring or rewriting, keep every comment that is still true — deleting the reasoning behind a subtle line is a regression even if the code still runs. Do not add comments that restate the code.
- **Do not add compiler or linter warnings.** Baseline: `cargo check` reports 13 warnings and `npx oxlint` 5, all pre-existing. Yours should add zero.
- Build checks before you say something compiles: `cargo check` in `backend/`, `npx tsc -b` in `frontend/`.

## Backend rules (Rust)
- **Propagate errors with `?`.** Handlers and middleware return `Result<_, ErrorService>` (an `ErrorService` is itself a valid HTTP response, so a middleware can return it too). Use `?`, `.map_err(..)`, `.ok_or_else(..)`. Do not hand-write `match x { Ok(v) => v, Err(e) => return … }` or `let Some(x) = … else { return … }` just to pass an error along. A manual `match` / `if let Err` is right only when you *intend* to swallow the error (log and continue, best-effort work, fall back to a default) — then say so in a comment.
- **One handler per file** in `src/routes/<domain>/`, each with a `#[utoipa::path]` annotation; the domain's `router.rs` builds the `Router` and an `ApiDoc`, which `routes/router.rs::openapi()` merges. Request/response structs are `pub(crate)` and derive `ToSchema`. A new route goes in the authenticated router (`router()`) unless it genuinely must be public (login, first-run setup — see `public_router()`); an owner-only handler takes the `OwnerUser` extractor instead of `AuthUser`; anything per-user filters by the caller's id and checks ownership (e.g. `chat_store.owned_chat`), returning 404 for someone else's resource.
- **Each store owns its tables.** Every `services/*_store.rs` reaches the database through its own private SeaORM entities and its own error enum (converted `From<…> for ErrorService`). Raw SQL belongs only in `services/migrate.rs` and `services/bootstrap.rs`. If a store needs data another store owns, inject that store and call its method (or, for one column, a read-only projection entity) — never query the other store's table directly. Put logic in the service that owns the concept (password hashing lives in `AuthService`, not in the user store).
- **Uniqueness and races are the database's job.** Enforce with a UNIQUE constraint or unique index and map the violation to a 409; do not "check, then insert". (Example: `users_one_owner`, a partial unique index, makes two simultaneous first-run requests create only one owner.)
- **Keep blocking work off the async runtime.** bcrypt, hashing large files and similar CPU-bound or blocking work goes through `tokio::task::spawn_blocking` (or tokio's async fs); otherwise every other request stalls behind it.
- **Treat client input as hostile.** An identifier that must be interpolated into SQL (Postgres cannot bind `CREATE DATABASE "<name>"`) is validated against a strict pattern. A path the client sends is resolved relative to a fixed root: reject absolute paths and `..`, canonicalize, and confirm the result is still inside the root (that also defeats symlinks). To an unauthenticated caller return a generic message; log the driver detail server-side.
- **Configuration lives in one file.** The backend reads no environment variables and no `.env` (except `RUST_LOG`). Every setting is a field with a default in `backend/src/config.rs`, persisted in `backend/data/settings.json`. Adding a setting means: the field + default, both `backend/data/settings*.example.json` files, and the table in `backend/README.md`.
- **Never destroy user data.** No "drop and recreate" migrations. A schema change is a versioned, data-preserving step in `services/migrate.rs` (see "One centralized migration" above). Code that moves or copies user data must be all-or-nothing (one transaction), preserve ids, and leave the original as a backup. Test the upgrade against a realistic *old-schema* database: create the old tables with rows, run the migration, compare the result table by table.
- **Long operations are background tasks.** Anything that can take minutes (model downloads, imports) starts a task, returns `202` with a task record, and is watched through a polling endpoint — never a request held open. Give each such task a way to report progress and its failure reason.

## Frontend rules (React + TypeScript)
- **Use the primitives** (`Div`, `Label`, `Button`, `Input`, `Select`, `Checkbox`, … in `src/components/primitives`) rather than raw HTML tags, unless no primitive fits.
- **No literal colors in component styles.** Use the theme variables (`--color-primary`, `--color-secondary`, `--color-tertiary`, and the derived `--color-surface`, `--color-border`, `--color-danger`, … defined in `src/styles/variants.scss`). A theme file in `src/themes/` fills in only the three palette colors. Read `frontend/THEMING.md` before touching either.
- **Authenticated resources go through axios.** A browser sends no `Authorization` header for `<img src>`, `<video src>` or `<a href>`, so a bare URL to a protected endpoint fails. Fetch through axios (which attaches the token) and use a `blob:` URL (see `hooks/use-file-blob-url.ts`, `api/files/download.ts`).
- **Session rules.** Only a `401` ends a session; a network error or 5xx keeps it and retries. Never use `window.location.assign` for in-app navigation — change state and let the route guards / `<Navigate>` redirect, so nothing reloads.
- **UI mirrors, backend decides.** Hide owner-only controls from other users, but the backend's `OwnerUser` check is the real gate. Ask for confirmation inside the UI (not `window.confirm`) before destructive actions.
- **Structure.** One file per endpoint in `src/api/<domain>/` with shared types in that folder's `types.ts`. Split a large component by responsibility (the setup wizard is a shell plus one hook per step in `pages/setup/steps/`).

## Verify before claiming something works — additions
- **Test against the real dependency when the change touches it.** Ollama behavior (pull, import, vision, tool calls) is verified against a real Ollama container — a CPU-only one is fine for anything that only registers or inspects a model. Postgres behavior against a throwaway container. Do not assume an API works the way you expect: state the assumption, then run it. Example: "a second `.gguf` in `/api/create` becomes a vision projector" was only an assumption until an actual model + projector pair was imported and shown to answer questions about an image.
- **Say what is unverified.** If you could not run something, say exactly that instead of implying it works.
- **Playwright tips for this UI.** The Python Playwright package may not match the browsers downloaded for it: launch with `executable_path='/usr/bin/chromium'` and `args=['--no-sandbox']`. The backend's dev CORS allows only an origin ending in `:5173`; to test a second dev server on another port add `--disable-web-security`. Section headings are styled uppercase, so `inner_text` returns them uppercase — compare case-insensitively. Locators like `text=Change` match substrings case-insensitively (they can hit helper text) — prefer `get_by_role('button', name='Change', exact=True)`. The setup wizard keeps every step mounted, so scope inputs by placeholder, not by `input[type=…]`. Playwright callbacks only fire while a Playwright call is running — wait with `page.wait_for_timeout`, not `time.sleep`.
- **Clean up.** Remove temporary tests (`temp_verify` modules), stop every process and container you started, delete scratch files, and confirm with `git status` that only intended files changed.

## Writing docs and comments: no diff language against something that never shipped
Describe current behavior, not "now does X instead of Y" — *unless* Y was a real, previously-released behavior a user could have actually seen. Comparing against an intermediate state that only ever existed mid-development (this session's own iteration, never tagged/released) is meaningless to anyone who wasn't watching that session happen — from their side, it's just a new feature, full stop. This applies to rustdoc/JSDoc comments and `CHANGELOG.md`/`README.md` alike. (A `CHANGELOG.md` "Fixed"/"Changed" entry is the one place real version-to-version diffing belongs — that's the whole point of those sections — as long as the "before" state was actually shipped.)

## System prompt (`SYSTEM_PROMPT` in `backend/src/facade/agent.rs`)
Word a behavioral rule as a check to run ("before doing X, check Y"), not a capability fact ("you can/can't do X"). A fact goes stale the moment something changes and causes a false refusal; a check stays correct regardless. Keep the array in sync with `backend/src/tools/os/execute_command.rs`'s own baked-tool-list text when either changes — they're meant to describe the same reality.

## Git
Never add attribution lines (`Co-Authored-By`, a session/tool URL, etc.) to a commit message or PR description, in this repo, ever.
